### 이번 패치에 포함

1. 기존 육각 섹터를 **기초/탐사 섹터**로 그대로 보존한다.

3. **기초 섹터 보기 / 행정 섹터 보기** 전환, 통합된 섹터의 내부 경계 페이드 및 행정구역 외곽선 강조를 구현한다.
4. 연결된 기초 섹터들을 선택하여 행정구역 생성·확장·통합·이름 변경·해제할 수 있게 한다.
5. 최소한의 **로컬 영속 저장**으로 행정 편집 결과를 새로고침 후에도 복구한다.
6. 현재의 게임 시간 배속 상수·모델·HUD를 새 규칙으로 교체하고, 0.1×~100× 배속·일시정지·실시간 정확성·시각 표시를 검증한다.
7. 후속 정책·행성 소속·위험 상황 자동 감속·오프라인 정산을 붙이기 쉬운 **공용 계약/API**만 확보한다.

### 이번 패치에서 제외

- 지구 인구·인류 문명 실제 게임 상태, POP 성장, 행성/시설 건설, 정부·민간 경제, 투자·세금·시장.

## 1. 현행 v0.4 코드에서 반드시 이해할 구조

- `dist/src/system-context.js`: `createSystemContext()`가 모든 항성계의 공용 컨텍스트이며, 태양계 전용 로직은 `createSolContext()` 어댑터에 있다.
- `dist/src/hex-sectors.js`: 고정 반경 `HEX_SECTOR_RADIUS_GAME_AU = 210`; axial `(q,r)`; `sectorId(systemId,q,r)`는 `${systemId}:${q}:${r}`; 시스템 크기에 따라 링 수만 변함.
- `dist/src/sector-view.js`: 기존 기초 섹터의 렌더링·선택·호버·전역 `LineSegments`를 제공하며 임의로 기울어진 평면을 지원한다.
- `dist/src/scene.js`: `SystemViewer`의 카메라, 천체 우선 선택, 섹터 ray pick, 시스템 전환/리소스 정리.
- `dist/src/context-panel.js`: 화면상 천체/섹터 옆 정보창. 천체 선택만으로 자동 줌하지 않음.
- `dist/src/main.js`, `dist/index.html`, `dist/style.css`: 작은 HUD, 지금은 `1× / 10× / 50×` 버튼.
- `dist/src/model.js`의 `Simulation.advance(seconds)`는 현재 `seconds * BASE_DAYS_PER_SECOND * speed`를 사용하고, `dist/src/data.js`의 **`BASE_DAYS_PER_SECOND = 0.02`는 새로 확정한 시간 기준과 완전히 다르다.** 배속 버튼만 변경하지 말고 **실제 모델의 시간 환산부터 교체할 것**.
- `dist/src/main.js`의 현재 애니메이션 루프는 `Math.min(frameDelta, .1)`로 프레임 경과 시간을 자른다. 새 시간 기준에서 의도치 않게 게임 시계가 실제 경과시간보다 느려지지 않도록, 숨김/정지 및 장기 프레임 지연 정책과 함께 점검할 것.

원본 항성계의 게임 AU/월드 비율 `140/53`, 태양/행성 크기, v0.4의 테스트 성과(36개 기록), 모바일 가로 조작은 보존한다. 태양계만 동작하는 분기는 공용 행정 모델·뷰·시간 제어에 넣지 않는다.

## 2. 기초 섹터와 행정구역의 개념적 계약

### 기초 섹터(Base / Exploration Sector)

- 3차원 우주의 좌표를 고정된 육각 구획에 매핑하는 **공간적 단위**.
- 크기·중심·좌표·ID·이웃 관계는 v0.4와 동일.
- 탐사 상태/발견 자원/향후 이동·탐색의 기준. 행정 통합으로 없어지거나 크기가 바뀌지 않는다.
- 행성과 함선의 `currentSectorId`는 위치에 따라 변할 수 있으며, 물리적 이동과 행정 편집을 서로 혼동하지 않는다.

### 행정구역(Administrative Region)

- 한 **항성계 안**의 기초 섹터 ID 여러 개를 묶는 상위 **논리적 관리 구역**.
- 기본 섹터는 실제로 합쳐지지 않는다. 행정구역은 **기초 섹터 ID의 집합**만 보관한다.
- `administrativeRegionId`(향후 행성/거점의 고정 행정 소속)와 `currentSectorId`는 서로 다른 차원임. **행성이 공전하여 기초 섹터를 벗어나도 자동으로 행정구역 소속을 바꾸지 않는다.** 이번 패치에서 행성 소속을 아직 생성하지 않아도 그 계약은 문서화한다.
- 지역 경제/자원은 후속 단계에서 실제 행성·창고의 재고를 집계할 것이며, **행정구역이 행성 재고를 복제해서 보유하지 않는다.**

### 최소 데이터 구조 (예시)

```js
{
  schemaVersion: 1,
  systems: {
    sol: {
      regions: [
        {
          id: 'sol:admin:1',           // 한번 발급하면 이름·섹터 통합 뒤에도 안정
          systemId: 'sol',
          name: '내행성 행정구',
          color: '#80b8a8',          // 미리 정의한 절제된 색 팔레트 사용 가능
          sectorIds: ['sol:0:0', 'sol:1:0', 'sol:0:1']
        }
      ],
      nextRegionSerial: 2
    }
  }
}
```

정확한 내부 자료구조는 필요에 따라 Map/Set 등으로 구현해도 좋지만, **영속 저장은 버전 있는 JSON, 시스템별 구역, 안정 ID**라는 계약을 지켜라. 잘못된 JSON/오래된 버전/존재하지 않는 ID는 안전하게 검증·복구/거부하고 화면을 깨뜨리지 말 것. 저장한 지역을 다른 항성계로 잘못 불러오면 안 됨.

**초기 상태:** 모든 항성계의 기초 섹터는 별도의 사용자 행정구역에 자동 귀속시키지 않아도 된다. 미지정 상태가 가능해야 한다. 플레이어가 중심 `sol:0:0`에서 첫 행정구역을 만들고 인접 섹터를 붙일 수 있게 할 것. 태양계 중심=내행성계라는 우연한 배치를 전역 규칙으로 하드코딩하지 말 것.

### 데이터 유효성 규칙

1. 존재하는 기초 섹터 ID만 포함; 동일 구역 내 중복 ID 금지.
2. **하나의 기초 섹터는 같은 항성계 안의 둘 이상의 행정구역에 동시에 속할 수 없다.**
3. 행정구역은 최소 1개 섹터를 포함하고 **공유 변을 통한 연결성**을 유지한다(꼭짓점 접촉만으로는 연결되지 않음).
4. 단, **고리 모양/가운데가 빈 구역(hole)은 허용**한다. 육각 링 전체를 행정구역으로 지정하고 내부 중심 칸은 다른 구역으로 관리할 수 있어야 한다. 안쪽 구멍의 경계도 구역 외곽선으로 취급한다.
5. 연결이 끊어지는 제거/분할은 명시적으로 막거나, 사용자가 이해하는 별도 분할 연산으로 처리. 이 패치에서는 연결 단절 시 **거부 + 이유 표시**가 안전하다.
6. 링이 확장되어도 기존 섹터 ID와 구역 배정은 변하지 않는다. 새로 추가된 기초 섹터는 기본적으로 행정구 미지정.
7. 한 구역을 다른 구역에 **통합**할 때, 대상 구역 ID를 유지하고 흡수된 구역을 제거한다. 합병된 모든 sector ID는 대상 구역으로 재귀속; 이름/색은 대상 구역이 유지(편집으로 나중에 변경 가능). 서로 인접하지 않는 두 구역의 직접 통합은 거부한다.
8. 구역의 ID에 사용자 이름/행성 이름/현재 궤도 위치를 넣지 말 것.

## 3. 행정 섹터 지도 시각화 — 가장 중요한 UI 요구사항

### 화면 모드

**A. 기초 섹터 보기(탐사 지도)**

- v0.4처럼 모든 기본 육각형의 경계를 읽기 쉬운 약한 선으로 표시.
- 행정 통합 상태와 관계없이 기본 셀 테두리는 **전부 복구**된다.
- 기존 천체 선택/정보 탭, 호버, 섹터 토글, 카메라 동작 보존.

**B. 행정 섹터 보기(행정 지도)**

- 구역에 속한 기초 셀은 **매우 얇은 반투명 구역 색 면**으로 표시할 수 있다.
- **서로 인접한 두 기초 셀이 같은 행정구역에 속할 때**, 그 둘 사이의 공유 경계선을 **거의 보이지 않게 페이드**한다.
- **다른 구역 간 경계 / 구역과 미지정 칸의 경계 / 격자의 바깥 테두리**는 분명히 보여준다.
- 구역에 속하지 않은 두 셀 사이의 경계는 **그대로 섹터 경계로 보존**한다. `null === null`이라고 둘을 한 구역으로 취급하면 안 된다.
- 같은 구역은 연속된 하나의 면처럼 느껴져야 하며, 외곽 경계를 따라 윤곽이 이어져야 한다. 고리 형태라면 안쪽 구멍 경계도 표시.
- 색을 너무 진하게 채워 행성·항성·궤도·선택 정보탭을 가리지 말 것. 기울어진 3D 기준 평면에서 기존과 같은 정렬·깊이·페이드를 유지한다.
- 편집 중 미리 선택한 셀과 통합 대상 구역은 구분되도록 미리보기 표시. 실제 반영은 명시적인 적용 버튼 시점.

#### 시각 강도 제안(확정 수치 아님)

| 종류 | 상대적 시각 강조 |
|---|---|
| 기초 지도 일반 경계 | 기존 기본선 수준 (`opacity ≈ 0.17` 참고) |
| 행정 지도 구역 **내부** 공유 경계 | 매우 희미하게 (`~0.02–0.04` 참고) |
| 행정 지도 **구역 외곽** 경계 | 명확히 보이게 (`~0.45–0.65` 참고) |
| 행정 지도 선택 구역 외곽 | 더욱 분명하게 (`~0.8` 참고) |
| 행정 구역 면 채색 | 매우 약하게 (`~0.05–0.12` 참고) |

이 값은 화면/모바일 및 낮은 알파의 인지성을 보고 조정한다. **핵심은 수치가 아니라 내부선 < 일반선 < 외곽선의 시각적 위계**다.

#### 기하/렌더링 주의

- **절대로** 육각형을 합친다는 이유로 `hex-sectors.js`의 좌표, 육각형 크기, 셀 다각형/ID를 변형하지 않는다.
- 기본 경계 `LineSegments` 하나의 전체 opacity만 낮추는 것으로는 내부 경계만 희미하게 만들 수 없음. **공유 변의 양쪽 행정구역 ID를 비교하여 내부 변/외곽 변을 분류**하고 서로 다른 배치 레이어/머티리얼(또는 꼭짓점 색/알파)을 사용한다.
- `gridLineSegments()`처럼 변을 **한 번만** 그려 이중 선분·진해진 경계/깜빡임을 방지. 두 셀의 공유 변에 대해 같은 구역이면 내부선, 다르면 경계선으로 단 한 번 분류.
- 행정 구역 생성/삭제/통합/이름·색 편집 또는 시스템 전환 시에만 경계 지오메트리를 다시 만든다. **매 프레임 / 마우스 이동마다 37~127칸 전체를 새로 생성하지 않는다.**
- `SectorView`를 유지하며 별도 `AdministrativeRegionView` 등을 구성하거나, 기존 view 안에 명확한 독립 레이어를 더한다. 좌표/이웃 수학은 기존 공용 함수 재사용.
- 전환/편집/전체보기/선택 해제 시 GPU geometry·material·이벤트 리스너의 누수가 없도록 `dispose` 구현.

개념 예시:

```text
기초 지도:          행정 지도에서 같은 4칸 통합:
[ A ][ B ]         [           행정구역 1           ]
[ C ][ D ]         [   내부 경계 흐림 / 외곽만 강조   ]

기초 섹터 A·B·C·D의 ID와 실좌표는 절대 그대로다.
```

## 4. 행정구역 편집 UX

### 기본 흐름

1. 상단 HUD 또는 같은 급의 접근하기 쉬운 컨트롤에 `탐사 섹터 | 행정 섹터` 보기 전환을 둔다. 기존 `섹터 표시/숨김` 토글의 의미가 모호해지지 않게 레이어 표시와 지도 모드를 구분한다.
2. 행정 지도에는 **보기 상태**와 **편집 상태**를 별도로 둔다. 보기 상태에서는 기존 천체·구역 조회가 가능하고, 편집 상태에서는 기본 셀 지정이 가능하다.
3. 편집 진입 → 셀 여러 개 선택 → `행정구역 생성` → 구역 이름 지정 → 적용. 이후 인접한 미지정 셀들을 `기존 행정구역에 추가`하거나, **인접한 기존 행정구역 두 개를 `통합`**한다.
4. 구역 이름 변경, 구역에 속한 셀 제거(연결성 검증), 구역 삭제(셀을 미지정 상태로 복귀), 선택 취소가 가능해야 한다.
5. 최소한 `링 전체 선택` 버튼을 제공한다. `hexRing(q,r)`을 이용해 0/1/2/3... 원하는 **기초 육각 링**을 일괄 선택하되, 이미 다른 행정구에 속한 칸이 있으면 명시적인 처리/충돌 확인을 거치도록 한다. 하나의 링이 중심 구멍을 형성하는 것은 정상이다.
6. 기초 육각 링과 **천체의 실제 공전 궤도는 별개**다. `궤도 반경/궤도 통과 셀 기준 자동 선택`은 향후 확장으로 남겨도 되며, 이번에 육각 링을 실제 행성 궤도처럼 잘못 표시하지 않는다.
7. 편집 결과는 즉시 행정 지도에 반영하되, **행정구역 미리보기와 확정 결과**를 구분해 사용자의 오입력을 막는다.

### 클릭·터치와 선택 우선순위

- **일반 보기**: 기존 `DOM UI → 천체 실제 메시 → 보조 천체 선택 → 기초 섹터` 우선순위를 보존한다.
- **행정 편집**: UI에 명시적으로 들어갔을 때만 `DOM UI → 기본 셀 편집 선택` 우선으로 바꾼다. 편집 중 태양/행성과 같은 평면 투영 위치에서 의도한 셀을 선택할 수 있어야 한다.
- 데스크톱: 셀 클릭으로 추가/해제, Shift+클릭 또는 별도 선택 도구 지원. 모바일: 명시적인 셀 선택 버튼/편집 모드로 멀티셀 편집 가능. 터치 드래그·핀치는 카메라 조작이며 우발적 선택/통합 금지.
- 드래그 5px 이상, 멀티터치, UI 위 클릭은 셀 선택으로 잘못 처리하지 않는다. 편집 중에도 카메라 회전·이동·줌 작동.
- 통합 대상이 겹치거나 연결되지 않을 경우 **실행 전에 검증 오류를 알려주고 원상태 유지**.
- 최소한 바로 이전 편집을 되돌릴 수 있는 `실행 취소`가 있으면 좋다. 긴 Undo/Redo 스택은 선택적.
- 모바일 844×390 및 667×375에서 편집 UI가 지도 전체나 하단 시간창을 계속 가리지 않도록 작은 드로어/접힘 UI 권장.

### 정보 표시

- 행정구역 이름, ID, 소속 기초 섹터 수, 포함된 링 범위, 색상, 현재 선택 상태.
- 지도상 현재 위치가 속한 기초 섹터와 현재 행정구역을 **서로 구분**하여 표시.
- 행정구역은 아직 경제/인구가 없으므로 가짜 주민 수/세금/산업 수치를 만들지 말 것. 비어 있거나 `추후 도입`으로 표기.
- 천체 선택 시 기존 정보 탭의 확대 버튼/위치 추적/가림 판정은 그대로 작동.

## 5. 행정구역 저장·불러오기

- 이 패치는 전체 게임 저장 시스템을 구현하지 않는다. **행정구역 편집 상태만** 이름공간이 분리된 `localStorage` 등에 버전 있는 JSON으로 저장한다.
- `schemaVersion`, `systemId`, `regionId`, `sectorIds`, `name`, `color` 등을 보관. 테스트/개발용 항성계와 태양계의 편집 상태는 분리.
- 저장은 **편집 성공 시**, 읽기는 해당 시스템 진입 시, 실패 복구는 오류 메시지/안전한 빈 상태로. 유효하지 않은 사용자 데이터가 기존 렌더러를 중단시키지 않아야 한다.
- `growHexGrid()`로 외곽 링이 추가된 뒤에도 기존 구역/섹터 배정 보존. 존재하지 않는 섹터 ID는 조용히 다른 좌표로 재배치하지 않는다.
- 이미 저장된 `schemaVersion`을 무시한 강제 덮어쓰기 금지. 버전 검증/복구 경로 문서화.
- **게임 시각/POP/오프라인/경제/항성계 물리 상태를 저장·복원하는 것처럼 보이게 구현하지 말 것.** 행정 편집만 영속화한다.

## 6. 시간 시스템: 새 배속과 정확한 환산

### 기본 원칙

**게임 내 시계는 하나**다. UI에서 속도를 선택하면 게임 세계에서 경과하는 시간을 바꾼다. `1×`의 의미는 `게임 시간 10초 / 현실 시간 1초`이다.

공식:

```js
const BASE_GAME_SECONDS_PER_REAL_SECOND = 10;
const gameSecondsAdvanced = realElapsedSeconds * BASE_GAME_SECONDS_PER_REAL_SECOND * effectiveSpeed;
const daysAdvanced = gameSecondsAdvanced / 86400;
```

예시:

| 표시 배속 | 게임 시간/현실 1초 | 설명 |
|---:|---:|---|
| 일시정지 | 0초 | 시계 동결 |
| `0.1×` | 1초 | 현실 시간 1:1, 전술 최저 기본값 |
| `0.25×` | 2.5초 | 전술 |
| `0.5×` | 5초 | 전술 |
| `0.75×` | 7.5초 | 전술 |
| `1×` | 10초 | **기본 전략 배속**, 전술 허용 상한 |
| `2×` | 20초 | 전략 |
| `5×` | 50초 | 전략 |
| `10×` | 100초 | 전략 |
| `50×` | 500초 | 전략 |
| `100×` | 1,000초 | **최대 전략 배속** |

- 실제 1초 × `100×` → 게임 1,000초, 즉 16분 40초 진행.
- 실제 60초 × `1×` → 게임 600초, 즉 10분 진행.
- **기존 `BASE_DAYS_PER_SECOND=0.02`는 현실 대비 1,728배라는 과거 프로토타입 값**이므로, 이를 기준으로 100배를 곱하면 안 된다. 모든 시간 진행 경로를 새 환산으로 통일하고 상수/설명/테스트 중 오래된 참조를 정리한다.
- 모델의 `Simulation.days`는 기존 궤도에 입력하는 게임 날짜 경과량(일 단위)을 유지. NASA/JPL 천체력 데이터나 케플러/자전 계산식은 수정하지 말 것.
- 게임 날짜/시간 표시를 `YYYY.MM.DD HH:mm:ss` 등으로 확장한다. 배속이 낮으면 일자만 보이고 변화가 없는 것처럼 느껴질 수 있으므로 시·분·초 표시가 필요하다. 월드 표준 시계는 UTC 기준이거나 명시적 통일 표준을 사용한다.

### UI와 정책 구분

- 타임라인에는 `일시정지/재개`, 현재 배속과 조작 가능한 속도 메뉴를 둔다. 작은 모바일 화면에 10개 버튼을 무리하게 늘어놓지 않는다.
- 전술 프리셋 `0.1 / 0.25 / 0.5 / 0.75 / 1×`, 전략 프리셋 `1 / 2 / 5 / 10 / 50 / 100×` 중 선택 가능하게 한다. 사용자가 편히 조절하도록 명료한 UI. **전술/전략은 별도의 게임 달력이 아닌 허용 배속 범위**다.
- 향후 전투·미확보 공간에서 `effectiveSpeed <= 1`의 **제한 정책**을 적용할 수 있도록, `requestedSpeed`, `effectiveSpeed`, `speedCap`, `paused` 개념을 모델/컨트롤러에서 분리한다.
- 위험 진입 시 기본적으로 0.1×로 감속하되 플레이어는 전술 범위 0.1~1×에서 선택 가능하다는 **후속 연계 계약**을 문서화한다. 현재 실제 함선·위협 판정이 없으므로 가짜 전투 트리거나 자동 위험 감지는 만들지 않는다.
- 현재 패치에서 속도 제한 API를 구현한다면 `setSpeedCap(1)`/해제 등 순수 모델 테스트만 작성하고 실제 위험 발생에 연결하지 않는다. 제한이 풀리면 사용자가 요청했던 전략 배속을 어떻게 복원할지 명시하고 테스트할 것. UI의 표시 배속은 **실효 속도**와 어긋나지 않아야 한다.
- 기존 `Space` 일시정지, `H` 전체보기, `Esc` 선택 해제, 카메라 조작은 유지.
- 새로고침하면 기본 1×로 시작하고, 우연히 이전 세션의 100×를 자동 재개하지 않는 방식을 권장한다. 게임 전체 저장 기능이 생기면 다시 협의.

### 시간 누적 정확성

- `requestAnimationFrame` 경과 시간과 게임 시계의 관계를 검증한다. `Math.min((now-last)/1000, 0.1)`처럼 **정상적인 전경 프레임 지연을 무조건 잘라 실제 플레이 시간 자체를 누락하지 않도록** 보완한다. 큰 프레임 간격을 처리할 때는 모드/가시성/시스템 정지 여부를 확인하고 보수적인 복구 정책을 문서화한다.
- `document.hidden`일 때는 지금처럼 **게임 시간을 진행시키지 않는다**. 숨김에서 복귀한 첫 프레임에 숨겨져 있던 실제 경과시간을 한꺼번에 적용하지 않도록 시각 기준을 갱신한다. 이것은 **오프라인 정산 구현이 아니다**.
- 잠시 렌더링이 느려져도 `Simulation.advance()`는 결정적이고 같은 총 경과시간/배속이면 같은 `days` 결과를 낼 것.
- 초고배속의 큰 경과량을 무리하게 세부 시뮬레이션 반복 실행하지 않는다. 장래 함선·위험 이벤트에서는 **이벤트 발생 시각을 넘지 않는 게임 시계 갱신**을 지원할 수 있도록 함수를 분리하되, 이번에 가짜 전투/함선을 만들지 않는다.

### 아직 구현하지 않는 오프라인 규칙(문서화만)

| 항목 | 미래 적용값 |
|---|---|
| 게임 기본 UI 1× | 현실 대비 10배 |
| 오프라인 고정 배속 | UI 기준 1.25× = 현실 대비 12.5배 |
| 오프라인 진행 한도 | 게임 시간 최대 60일(초기 모델은 2개월 ≈60일) |
| 전투/위험 탐사 중 종료 | 전체 세계 시계 정지 |
| 위험 진입 직전 오프라인 경과 | 이벤트 시각에서 정지 예정 |

**현재 패치에서는 저장 시각으로 시간 정산하거나 크레딧/자원을 지급하지 않는다.**

## 8. 반드시 통과할 검증 기준

### A. 행정 구역의 순수 모델 검사

1. Sol의 37칸, 소형 1칸, 대형 127칸을 **기존과 동일**하게 생성할 것.
2. 중심 칸 포함 연결된 4개 셀을 구역 1로 생성하면 해당 구역에서만 내부 공유 변이 페이드 대상이 됨.
3. 서로 다른 구역 또는 미지정 셀 사이의 경계는 보존. **미지정–미지정 경계가 사라지지 않음.**
4. 1링 6칸만 통합한 **구멍 있는 링 형태**를 합법적 구역으로 처리; 외곽·내곽 모두 경계가 생성됨.
5. 꼭짓점 접촉만 한 두 셀 / 떨어진 두 구역의 통합을 거부.
6. 두 인접 행정구역 병합 후 공유 변이 내부선으로 바뀌며, 대상 ID는 유지하고 흡수된 ID는 제거.
7. 기존 구역에서 셀 제거 시 연결이 끊어지면 거부; 셀 추가/삭제 및 이름 변경 시 무관한 구역 불변.
8. 한 셀이 두 행정구역에 중복 지정되는 오류 차단.
9. `growHexGrid()`로 그리드를 확장해도 기존 할당·위치·ID 보존.
10. 한 항성계의 구역을 다른 항성계로 오염시키지 않음. 저장/로드 동등성, 잘못된 JSON/섹터 ID 안전 처리.

### B. 시간 계산 검사

1. 전경 현실 60초, 기본 `1×` → 게임 시간 정확히 600초.
2. 전경 현실 1초, `0.1×` → 1초, `0.5×` → 5초, `100×` → 1000초.
3. `100×` 상한 초과 입력 거부 또는 안전한 제한. 음수·NaN·Infinity 배속 거부.
4. 10번의 0.1초 갱신과 1번의 1초 갱신 결과 일치(허용 오차 내).
5. 일시정지 중 증가 0; 재개 후 지정 배속 정확.
6. 모의 speedCap=1에서 요청 100×는 실제 1× 이하, cap 해제 후 정책에 맞는 복원.
7. 시스템 날짜/시간 표시는 UTC 또는 선택한 단일 시간 규칙을 지킴; 일/월/연 경계 정상.
8. 숨김→복귀 뒤 숨겨진 시간 일괄 적용 금지; 전경의 정상 프레임 지연은 조용히 누락하지 않음.
9. 기존 궤도/크기/텍스처/선택 회귀 테스트와 충돌하지 않음. 기존 테스트가 구형 시간 상수에 의존하면 **기대값을 새 계약에 맞게 수정하고 근거 기록** (테스트 삭제 금지).

### C. 브라우저·모바일 상호작용

1. 기초 모드→행정 모드→기초 모드 전환 시 기본 모든 선 복구; 선택된 4칸은 행정 모드에서 한 구역처럼 보임.
2. 행정구역 이름 변경, 인접 추가, 두 구역 통합, 셀 제거, 구역 삭제, 링 선택, 페이지 새로고침 후 복원.
3. 기초 모드에서 기존 천체 우선 클릭·달 보조 선택·천체 옆 탭·확대 버튼·공전 추적 그대로 유지.
4. 행정 편집 모드에서만 셀 우선 클릭. 드래그·핀치·다중 터치가 실제 통합으로 오인되지 않음.
5. 경사진 다중 항성 시험계에서 행정구역 외곽선과 클릭·셀 ID가 정확히 일치.
6. 844×390/667×375 모바일 가로에서 행정 도구와 시간 컨트롤 접근 가능; 주요 UI/지구·달 선택이 완전히 가려지지 않음.
7. 0.1×/1×/100× 시간 디스플레이 실제 흐름 테스트; 일시정지, 속도 표시, 설정/숨김 처리.
8. 반복 시스템 전환과 행정 편집/삭제 후 DOM 이벤트·Three.js geometry/material 누수, 미처리 JS 예외, 콘솔 오류 없음.
9. `npm run check`, `npm test`, 실제 Chromium/Playwright 브라우저 검사, `git diff --check` 모두 기록. 실기기 성능 미검증이면 솔직히 한계 표시.

## 최종 수용 조건 요약

**같은 행정구에 속한 섹터들이 내부 경계를 거의 잃고 하나의 영역처럼 보이면서도, 탐사 섹터 모드에서는 원래의 육각 격자가 100% 그대로 남아 있어야 한다.** 여러 섹터를 선택하여 실질적으로 행정구역을 생성·병합·해제하고 새로고침 후 보존할 수 있어야 한다. 동시에 시간 `1× = 현실 대비 10배`, 전술 `0.1~1×`, 전략 최대 `100×`가 **실제 게임 시계 계산과 UI에서 모두 일치**해야 한다.
