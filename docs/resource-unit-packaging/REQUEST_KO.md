## 0. 작업 목표 및 우선순위

기존 경제·산업·지질·게임 데이터를 보존하면서 자원 U의 물리적 의미와 재고 구조를 확장한다. 향후 수소뿐 아니라 다른 가스, 액체, 반물질, 아스트로지늄, 미정의 특수 자원도 **코드 변경을 최소화한 데이터 기반 레시피**로 포장·소비·소재 회수·기술 세대교체할 수 있는 기반을 만든다.

순서: **(1) 기존 코드/저장 영향 분석 → (2) 자원 규격 정의 → (3) 범용 패키징/재고/거래 엔진 → (4) 현행 산업 연결 및 구버전 이관 → (5) 자동 개선 기본 규칙 → (6) 회귀 및 보존 검증 → (7) 구현 보고서.**

- 게임 본체에서 실제로 쓸 수 있는 모듈과 저장 구조를 만들어라. 개념 문서만 작성하고 끝내지 말 것.
- 코덱스가 사용자 승인 없이 경제·발전 비용이나 연구 기술 수치를 결정하거나 기존 합격 여부를 바꾸지 말 것.
- 새로운 구현은 기존 열려 있는 PR 및 브랜치 체인과 충돌하지 않도록 **위 브랜치의 최신 커밋을 기준으로 별도 구현 브랜치/PR**로 분리하는 편을 우선한다. 원격 HEAD가 바뀌었으면 먼저 확인하고 정확히 기록할 것. `main`에 직접 쓰거나 기존 PR을 임의 병합하지 말 것.

## 1. 이미 결정된 설계 — 이것을 재해석하거나 무단 변경하지 말 것

### 1.1 U는 **하나의 통일된 자원·화물·보관 단위**

1. 게임에서 자원 재고는 U로 표기한다. 함선 화물창과 행성 저장시설도 U 용량을 사용한다.
2. **모든 자원 1U는 동일한 1U의 표준 화물·보관 공간을 점유한다.** 예: 함선 화물창 `100U`면 광석이든 수소든 합계 최대 `100U`를 싣는다. `수소 1U = 화물 0.2U` 같은 자원별 적재계수는 만들지 말 것.
3. 자원별 **1U의 실제 내용물 질량**은 다르다.
   - `ore`: **1U = 10,000kg = 10톤**.
   - `alloy`: **1U = 10,000kg = 10톤**. 금속/합금 전체를 아우르는 추상 산업자원이지 알루미늄만 의미하지 않는다.
   - `hydrogen`: **1U = 액화수소 내용물 500kg = 0.5톤**. 패키징 소재·탱크 등의 질량은 내용물과 별개.
   - 다른 자원: 아직 미정. 임의로 확정하지 말고 나중에 정의 가능하게 할 것.
4. U의 기준이 광석 10톤이라는 것과 **고정된 SI 부피(m³) 10을 확정한다는 것은 다르다.** 이전 대화의 약 `10m³`는 가상 설명이었고 공식 상수로 고정하지 않는다. 이번 작업에서 또 다른 화물 단위, m³ 기반 적재 배수, 별도 가스 화물 포인트 등을 새로 도입하지 말 것.
5. 함선의 추후 물리 시뮬레이션에 실제 화물 질량이 필요하다면 자원별 `contentMassKgPerU`와 포장재 실제 질량에서 *내부적으로 유도*할 수 있도록 메타데이터를 준비해도 된다. **공간/창고 용량 계산은 끝까지 U 하나**로 하고, 이번 작업에서 새로운 함선 질량·가속·화물 UI를 구현하지 않는다.
6. **1U당 내용물 질량은 기술 발전으로 변하지 않는다.** 신기술은 같은 U를 위한 포장 재료량·회수율·전력·C·안전성과 같은 규격을 바꾼다.
7. `credits`는 화폐 `C`이지 포장 가능한 물질 자원 U가 아니다.

### 1.2 자원 분류와 저장 방식

- 분류 예: `ore/bulk`, `metal/bulk`, `gas/packaged`, `liquid/packaged`, `exotic/packaged`. 정확한 enum 이름은 코드 스타일에 맞춰도 되지만 분류와 포장 필요 여부를 분리해라.
- 기존 `ore`, `alloy`는 **벌크형**, `hydrogen`은 **패키지형**으로 시작한다. `residue` 등 현재 산업 내부 자원은 기존 동작을 보존하면서 적절히 명시한다.
- 특수 자원은 나중에 자원 정의/레시피만 추가하면 작동하도록 설계한다. **`hydrogen` 전용 분기나 `alloy` 고정 포장비 필드는 금지**한다.
- 한 개의 1U 표준 화물 단위가 실제로 작은 수소 탱크 여러 개의 묶음일 수 있다. 개별 탱크/상자마다 객체를 만들 필요는 없다.

### 1.3 현재 산업의 수량 계약은 유지

- `FACILITY_TYPES`의 기존 국영 광업·제련 건설비/기간/처리량, 기존 수소 사용 U 수치는 이번에 임의 변경하지 않는다.
- 핵융합 5GW 모듈 정상 수소 **2.5U/월 = 물리적 수소 1.25톤/월**; 최초 기동 **5U = 2.5톤**; 모듈 건설 **5U = 2.5톤**. 이 숫자를 줄이거나 새 연료주기를 설계하지 말 것.
- 제련 보조 수소 최대 85U/월 = 42.5톤/월, 광업 수소 부산물 최대 100U/월 = 50톤/월, 제련단지 건설 수소 120U = 60톤. 기존 게임 U 소비/생산 계약을 보존하고 새 질량 메타데이터로 환산만 가능하게 할 것.
- 수소 시세 **0.4C/U와 1.2C/U는 비교 후보**일 뿐 최종 고정가격으로 승인되지 않았다. 이번 작업에서 가격을 1.2로 강제하지 않는다.

## 3. RESOURCE-UNIT-1: 데이터 기반 자원 규격

예시 형태(필드명은 권고이며 기존 스타일을 따르되 의미는 보존):

```js
{
  id: 'hydrogen',
  name: '수소',
  unit: 'U',
  category: 'gas',
  storageMode: 'packaged',
  contentMassKgPerU: 500,
  cargoUnitsPerU: 1,
  requiresPackage: true
}
```

- `ore`/`alloy`: `contentMassKgPerU:10000`; 패키지 비용 없이 U 재고로 취급.
- `hydrogen`: `500`; 포장 규격으로 관리.
- 화폐 `credits`: 별도 화폐 경로. kg/U나 화물 용량이 적용되지 않음.
- 자원 분류와 규격 등록 기능은 검증(중복 ID, 유효 수치, 기존 등록 규칙 보존)을 갖춘 확장형 레지스트리여야 함.
- 임의의 신규 자원에 질량이 정의되지 않았다면 `null/unconfigured`로 명시하여 잘못된 질량을 추정하지 말고, 해당 자원이 실제 패키징·물류 거래에 쓰이기 전 검증에서 명확한 오류를 제시.
- 새 화물 용량 API가 필요하면 `sum(quantityU)`로 처리한다. 자원별 추가 화물 배수, 포장 세대별 보관 공간 감축은 넣지 않는다.
- 가능하면 기존 `TONNES_PER_RESOURCE_U`는 **광석·합금의 역사적 기준**으로만 호환 유지하거나 해당 참조를 자원별 접근 함수로 교체. 수소의 질량 변환에서 절대 재사용 금지.

## 4. PACKAGING-1: 범용 패키징 레시피/규격

### 4.1 특정 자원 하드코딩 금지

패키지 규격은 별도, **불변(immutable) 식별자**로 등록한다. 한 자원에 다수 세대/규격이 공존 가능해야 한다.

```js
{
  id: 'hydrogen-pack-gen1',
  resourceId: 'hydrogen',
  generation: 1,
  materialInputs: [
    { resourceId: 'alloy', amountQPer1000Q: 50, recoveryRate: 0.90 }
    // 추후: 다른 금속, 아스트로지늄, 특수 소재 등 항목 추가 가능
  ],
  electricityKWhPerU: null,
  directCostCPerU: null,
  unlockedBy: null
}
```

**위 50Q/1U와 90%는 테스트/구조를 보여주는 예시일 뿐 실제 게임에 확정해서 적용하지 말 것.** `null`은 미결정임을 뜻하며, 실행 시 무상 포장으로 암묵적으로 해석하면 안 됨. 전력·C·소재가 확정된 레시피의 실제 포장 거래에만 사용한다.

- `materialInputs[]`는 임의 길이의 자원 요구사항. 재료마다 서로 다른 소비량/회수율을 지원. `alloy`라는 필드명을 포장 엔진 구조에 고정하지 말 것.
- 소재는 회수율 0이면 소모품, 회수율 1이면 이상적인 완전 회수 재료, 0~1 사이면 부분 회수 가능.
- `creditC`와 `electricity`는 별개 입력. 현금과 에너지를 물질 U 재고로 가장하지 말 것.
- 콘텐츠 수소 1U 자체는 포장 입력 소재와 별개. **같은 수소 1U를 충전하는 데 필요한 탱크 소재**를 정의하는 것임.
- 규격 `id`의 수치/레시피는 발급 이후 불변. 연구에서 변화가 생기면 `gen2` 같은 **새 규격 ID**를 생성하며 구형 재고를 소급 변경하지 말 것.
- 유효하지 않은 레시피, 음수 입력/회수율, 중복 자원 항목, 미등록 참조, 자기 포장/간접 순환에 따른 무한 재료 생성 가능성을 검증하고 실패 시 안전하게 중단한다.
- 고급 자원이 미등록 상태여도 이를 참조하는 레시피를 **활성화할 때 명시적 검증 실패**가 나도록 할 것. 향후 확장 지점은 남겨라.

### 4.2 실제 소재와 회수 장부

패키징 시점에 `소유자/행성`의 자유 소재 재고에서 사용량을 **실제 차감**하고, 패키지 재고에는 어떤 소재가 얼마나 묶여 있는지 기록한다.

- 생산한 `hydrogen`은 1U 증가. 소재 `alloy` 등을 패키지에 묶었다면 해당 자유 재고는 감소.
- **패키지 소재는 패키지 자체에 이미 포함**되어 있으므로 화물창 공간 1U를 추가 점유시키지 않는다. 다만 나중에 화물의 실제 총질량을 계산할 때 내용물+소재(필요 시 장치 자체)를 합산할 수 있다.
- 소비 시 수소 재고는 줄고, 그 패키지에 *실제로 투입·기록된 소재*만 회수율만큼 **실제 소비자/소유자의 현지 재고**로 반환. 나머지는 손실 기록.
- 재포장 시 구형 패키지 소재 회수 → 신형 패키지에 필요한 소재 추가 투입/보유 → C·전력 소비 → 새 규격 재고 생성. 전체 거래는 검증 후 원자적으로 커밋. **수소 내용물은 정확히 보존**해야 함.
- 이미 사용한 자원의 패키지를 다시 소비하거나, 회수량을 이중 적립하거나, 전력/현금 없이 비용 있는 재포장을 실행하지 못하게 하라.
- 한 행성의 정부/민간, 다른 천체의 정부 재고가 **자동 합쳐지지 않도록** 소유자와 천체 키를 필수로 지정. 거래/이전이 생기면 패키지 메타데이터와 묶인 소재 소유권이 함께 이전하도록 API를 설계하되, 물류망 자체는 구현하지 말 것.
- 저장 수량·소재 회수는 기존 **정수 Q(1U = 1000Q)** 기준을 최대한 재사용. 미량 거래 반올림으로 회수율이 100%를 넘거나 소재가 생성되는 일 없도록 **결정적 잔여분 처리**를 설계. 예를 들어 `0.001U`씩 수천 회 소비한 결과가 1U 일괄 소비와 물질 보존 면에서 모순되지 않아야 한다.
- 가능하면 `quotePack`, `commitPack`, `consumePackagedResource`, `quoteRepackage`, `commitRepackage` 등 순수 견적과 실행을 분리. 부족 시 상태가 부분 변경되지 않는 **all-or-nothing 트랜잭션**.

## 5. 재고 구조: 개별 상자 객체 대신 규격별 묶음

동일한 `bodyId / ownerId / resourceId / packageSpecId`를 가진 패키지들은 묶어서 관리한다. 예:

```js
{
  bodyId: 'earth',
  ownerId: 'human',
  resourceId: 'hydrogen',
  packageSpecId: 'hydrogen-pack-gen2',
  amountQ: 100000, // 100 U
  bondedMaterialsQ: { alloy: 3000 },
  recoveryRemainders: {}
}
```

위 수치는 데이터 형식 예시이고 경제 기본값 확정이 아니다.

- 필수 불변식: **기존 UI/건설 견적의 총 수소 재고 Q = 같은 행성/소유자의 모든 수소 패키지 묶음 Q 합계**.
- 두 개의 독립된 진실값(source of truth)을 방치하지 말 것. 현행 `ownerInventory(s,bodyId).hydrogen`와의 호환이 필요한 경우 합계를 파생/동기화하는 한 경로를 마련하고, `validateIndustryState`에서 일치 여부를 검사.
- 광석의 기존 `inventoryLots`(광맥 출처·품질·가공 난도)를 패키징 lot으로 대체하거나 손실시키지 말 것. **광석 품질 lot과 패키지 세대 lot은 다른 개념**이다.
- 새 기술 세대가 나와도 기존 묶음의 `packageSpecId`, 본래 투입된 소재/회수 기준은 유지된다.
- 미래 패키지 재료 종류가 추가되어도 `bondedMaterialsQ`는 자원 ID 기반 객체/맵으로 처리할 것.
- 동일 규격의 묶음을 합칠 때 소재 총량과 회수 잔여분까지 일관되게 합칠 것. 패키지별 객체를 수만 개 만드는 방식 금지.

## 6. 구형 우선 소비 + 자동 패키지 현대화

1. 같은 자원을 소비할 때는 **구형 규격 우선**. 세대가 같다면 규격 ID 등 결정적인 정렬 기준을 두어 저장/재실행에 따라 소비 순서가 달라지지 않게 할 것.
2. 새로운 생산은 **현재 해금된 최신 승인 규격**을 우선 적용. 기술 연구 시스템이 아직 연결되지 않았다면 `availablePackageSpecs(ownerId)`와 같은 주입형/설정형 인터페이스만 준비할 것. 기술 트리 개편은 이 작업의 범위 밖.
3. **자동 개선은 기본 ON을 지향**하되, 현실적으로 필요한 운영 제약을 반영해야 한다:
   - 해당 행성·소유자의 포장/재포장 설비 처리능력과 시간.
   - 충분한 자유 소재 재고·전력·C.
   - 필수 유지보수/생존·생산 수요를 침범하지 않는 여유 자원.
   - 곧 소비될 구형 재고는 불필요하게 재포장하지 않고 **그냥 먼저 소비**.
   - 경제성 없는 재포장은 실행하지 않음. 판단에 필요한 비용·미래 소비 정보가 미정이면 강제로 무료 전환하는 대신 보류 사유를 기록할 것.
4. **연구 완료 직후 일괄 자동 치환은 절대 금지.** 자동 개선은 실제 입력 지급/처리량/시간에 의해 점진적으로 일어난다.
5. 현재 실제 게임에는 행성 전력 및 비용이 완전히 연결되지 않았으므로, 이번 구현에서는 **정확한 자원 예약·견적·선행조건·작업 큐/처리 API를 구현하고, 입력 미결정 시 안전하게 대기**하는 단계도 허용된다. 유료 재포장을 공짜로 돌리는 임시 우회는 금지. 관련 테스트에서는 명시적인 가상 전력/C/소재 투입과 용량으로 정상 작동을 검증할 것.
6. UI는 평소 `수소 10,000U`처럼 **합계 재고만 간단히 표시**. 세대별 재고/자동화 상태는 필요하면 접는 상세 정보로만 표시. 복잡한 별도 패키지 관리 화면, 개별 탱크 명령 UI를 만들지 말 것.

## 7. 현재 게임 산업과의 연결 / 아직 미결정인 가격 처리

**핵심 난점:** 현행 게임 산업에는 완전한 전력·포장 C 비용 체계가 없고, 수소 생산/소비는 단순 수소 Q로 구현되어 있다. 이번 작업에서 0.05U 합금·90% 회수 같은 **설명용 숫자를 공식 비용으로 몰래 채택하지 말 것.**

따라서 다음 두 레이어를 명확히 분리한다.

### A. 실제 엔진(완성)

- 입력 소재·전력·C가 모두 명시된 규격에 대해 실제 포장, 소비, 소재 회수, 재포장, 세대별 재고, 재고 부족·취소·보존 검사를 완전히 구현한다.
- 테스트에서는 실제 소재 투입/회수/가격/에너지 차감의 원자적 동작을 통합 확인한다.
- 향후 확정 레시피와 전력·C 공급자를 연결하면 게임 산업에서 바로 활성화할 수 있게 한다.

### B. 현행 게임 호환(임시·명시적으로 표시)

- 이미 존재하는/개발 시나리오에서 주어진 수소 및 아직 공식 포장 레시피가 정해지지 않은 현행 광업 신규 수소는, **물리 내용물 500kg/U를 가지되 과거에 포장 재료를 투입했다고 가정하지 않는 `legacy/unpriced compatibility` 규격의 패키지 묶음**으로 처리할 수 있다.
- 해당 호환 규격은 **실제 묶인 소재 0, 소비 시 회수 0**이며, 가상의 포장 비용/수익을 발생시키지 않는다. 이를 정식 무상 생산 방식이나 신형 포장 기술로 제시하지 말 것. 호환 방식을 채택했다면 게임 화면/개발 문서와 구현 보고서에 **미가격화 임시 경로**임을 분명히 기록한다.
- 정식 패키지 레시피가 설정/승인되면 신규 생산에만 정식 규격을 적용하고, 구형 호환 재고는 위 자동 소비/재포장 규칙으로 자연히 줄어들게 한다.
- 게임의 광업 부산물·제련·건설 수소 생산/소비를 새 공통 재고 조작 API로 통과시키되 **기존 U 생산량·건설 견적·가동 결과는 회귀 유지**할 것. `inv.hydrogen +=/-=` 같은 직접 변경 경로가 있으면 추적/교체하고, 상태 합계와 묶음 간 검증을 추가한다.
- 원광 매장량, 원천 `hydrogenRemaining`의 U 정수 잔량, 추출량, 현금 수지에 임의 환산을 적용하여 20배/100배로 바꾸지 않는다. **이전 데이터의 U 수량 자체는 그대로**, 새 물리적 해석만 변경한다.

## 8. 저장 데이터 이관 — 가장 중요

현재 `industry-storage.js`는 필드가 정확하게 일치해야 하며, `INDUSTRY_SCHEMA_VERSION`/`schemaVersion`과 `space-project:industry:v1:...` 저장 키가 있다. 단순 필드 추가로 이전 세이브를 전부 거부하거나 덮어쓰면 안 된다.

필수 조건:

1. 이전 v1 저장 내용의 **기본 검증을 거친 후** 명시적인 v1→v2 이관 루틴 구현. 새 버전 번호·저장 키 정책은 기존 백업 체계와 호환되도록 선택하고 문서화.
2. **기존 원본 JSON을 반드시 별도 키로 백업**하고, 정상 이관된 경우에만 새 상태를 활성화. 사용자가 명시적으로 가져오는 JSON에도 동일한 검증/이관 정책.
3. v1의 `planetInventory[bodyId][ownerId].hydrogen` 전체 수량을 `legacy` 패키지 묶음으로 만들며, **이관 시 `bondedMaterialsQ={}`**로 기록한다. **소비 후 가짜 합금 회수 금지.**
4. 광석 `inventoryLots`, 품질, `oreRemaining/oreExtracted`, `hydrogenRemaining/hydrogenRecovered`, 시설, 건설 진행률, 출처 서명, 정부 재정, 건설 및 제련 `materialLedger`, 시계, 이벤트 기록 등을 변형하지 않는다.
5. 이전 상태와 신규 상태의 U 수량·재정·원천 총량이 정확히 같아야 한다. 같은 파일을 반복 이관해도 패키지가 중복 생성되지 않게 하고, 신규 버전의 재저장/재로드가 안정적이어야 한다.
6. 손상 파일·서명 불일치·알 수 없는 필드를 포함한 JSON에 대한 기존의 **차단/격리/원본 보존** 기조를 유지한다. 이전 버전이 아닌 임의 JSON을 자동으로 고쳐서 받아들이지 말 것.
7. 개발 fixture와 정상 캠페인, 행성별/소유자별 재고 격리 및 `transient` 모드의 동작을 회귀 테스트로 보존한다.
8. 회수 소재가 장부에 실제 유입될 수 있으므로 **총합계 = 초기 자유 재고 + 생산 + 실제 포장재 회수 − 건설·포장·기타 실소비**로 보존식을 확장한다. 물질은 사라지는 것이 아니라 묶임/손실/회수 중 하나로 처리되며, 회수율로 존재하지 않은 물질을 창조할 수 없다.

## 9. 경제 검증·물리 수지와의 명확한 경계

- **ECON-SIM-4는 이번 작업에서 실행/구현하지 않는다.** 탐색 512/128개, 20년 시뮬레이션, 가격 재보정, 발전소 회수기간 재산정, 후보 채택 등 전부 후속.
- 기존 ECON-SIM-1/2/3의 소스·설정·원시 데이터·보고서·해시를 **수정하거나 동일 이름으로 덮어쓰지 않는다.** 3차 시뮬레이션 결과를 이번 구현으로 신규 검증된 것처럼 주장하지 말 것.
- 다만 3차 모델의 종전 물리 가정 중 **`물 9U → 수소 1U + 산소 8U`는 자원마다 1U 질량이 달라진 새 설계에서 그대로 보존 법칙으로 쓸 수 없다**는 점을 **후속 수정 사항**으로 별도 문서/구현 보고서에 명시.
  - 새 수소 1U는 **500kg**. 물 분해의 순수 화학 양론 기준으로 물 약 **4,500kg** 투입 → 수소 **500kg** + 산소 약 **4,000kg** 발생(공정 손실 전).
  - 물/산소의 게임 U 규격은 아직 결정되지 않았으니 `물 9U`, `산소 8U`를 새 단위로 정당화하거나 수치 확정하지 말 것.
  - 포장 전력·재료·C와 수전해 자체의 전력은 별도로 산정해야 하며, 기존 테스트/보고서를 이번에 다시 작성하지 않는다.
- 수소의 정상 핵융합 소비 2.5U/월, 제련 보조 85U/월 등 U 계약은 **이번 작업에서 그대로 유지**. 해당 계약의 적절성, 원가·가격, 자원 보급 안정성은 ECON-SIM-4에서 검증.

## 10. 최소 통과 테스트 (반드시 자동화)

### A. 단위 / 공통 화물

- `ore 1U=10000kg`, `alloy 1U=10000kg`, `hydrogen 1U=500kg`를 정확히 검증.
- 100U 화물창에 어떤 자원 조합이든 총량이 100U 초과하면 거부; 수소만 500U를 싣는 등 별도 가스 공간 배율 적용 금지.
- `credits`를 물질/포장 대상에 넣으려 하면 거부.
- 기존 0.001U 정수 Q의 경계·매장량 보호를 회귀 검사.

### B. 범용 포장/회수

- 테스트에서 **수소 100U 포장에 합금 5U를 실제 차감**, 전량 소비 후 회수율 90%면 **합금 4.5U 반환 / 0.5U 손실**. 현금·전력도 명시 입력 시 정확히 차감.
- 동일 시나리오를 합금이 아닌 **임의 신규 소재 2종**으로 반복하여 엔진이 hydrogen/alloy 하드코딩이 아님을 증명.
- 회수율 0/1/중간값, 일부 소비, 여러 lot, 묶음 병합, 매우 작은 Q 단위 반복 거래에서 소재 복제·이중 회수·음수 잔액 없음.
- 재포장 시 구형 묶인 소재의 회수와 신형 투입을 모두 장부에 반영. 구형 패키지의 수소량과 신형 패키지의 수소량 합계 보존.
- 소유자·행성 분리, 패키징 비용 부족·정전·불충분한 처리능력에서는 **상태 완전 불변**.

### C. 세대교체 / 자동화

- 구형 1세대와 신형 2세대가 동시에 존재할 수 있음.
- 소비 시 1세대 우선, 생산 시 현재 해금된 2세대 우선.
- 기술 해금 직후 기존 재고는 그대로; 처리능력·자원·시간을 지급한 수량만 재포장.
- 필수 유지보수 보호량 아래에서는 자동 재포장 중지; 재고 부족, 비용/경제성 미정 시 무료 전환 금지.
- 동일 입력/시드/시간 분할에서 deterministic 결과.

### D. 구세이브 및 회귀

- 기존 v1 저장(개발 fixture 포함)을 가져와 모든 수량·국고·매장/생산 기록을 보존하고, `legacy` 수소를 소비해도 합금 회수 **0**.
- 반복 이관, export/import, 저장/로드, 손상 JSON/원본 보존/차단 검사.
- 기존 국영 광업·제련 테스트, 광석 로트/품질·매장량 합계, 시설 견적/건설·생산/수소 소모량 불변.
- `npm run check`, `npm test`, 가능한 관련 브라우저 회귀 테스트를 수행. 재현 가능한 명령과 통과/실패 건수를 기록. 테스트 환경 제약이 있으면 우회해 성공한 것처럼 쓰지 말고 정확히 보고.
- ECON-SIM-3 관련 파일/산출물 내용 해시 및 기존 통과 범위가 **바뀌지 않았음**을 확인. 게임 포장 메타데이터 개편 자체가 기존 3차의 경제적 정합성을 재승인한다는 뜻은 아님.

## 11. 범위 밖 / 하지 말아야 할 일

- ECON-SIM-4 계산·가격 채택·수소 시장 고정가 1.2C 도입.
- 패키지마다 3D 오브젝트를 만드는 물리 시뮬레이션 또는 독립 창고·화물 슬롯 객체 수천 개 생성.
- 자원별 화물 용량 배수, 새 m³/피트/톤 공간 단위 도입. **U 하나로 통일.**
- 새 함선 설계/화물·추진량 시뮬레이터, 행성 간 무료 재고 이동, 물류망 본 구현.
- 실제 연구 트리나 새 기술 비용·효과율 확정. **규격 ID와 해금 인터페이스만** 제공.
