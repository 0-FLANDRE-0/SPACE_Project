## 2. A — SCU 자동 현대화 경과시간 소급 정산 검증·보완 [우선]

### 2.1 관찰된 위험 경로

다음 파일을 우선 감사한다.

- `dist/src/industry-packaging.js`: `advanceIndustryPackaging()`에서 SCU 처리능력이 양수일 때만 `advanceContainerQueue()`를 호출하는 분기.

- `tests/cargo-industry-logistics.test.js`: 현재 **자동 큐 생성 경로**를 시험하는 `late SCU automation connection does not spend historical idle time`.

**재현해야 할 별개 시나리오(중요):**

1. 처리능력 미정/0인 채로 실제 산업 시계를 500일 진행. SCU 큐의 마지막 처리시각은 뒤처져 있을 수 있음.

4. 1시간 진행했을 때 **8SCU만 작업**해야 하며, 과거 500일이 한꺼번에 진행된 것으로 계산되어 즉시 완료되면 안 됨.

현재의 자동 생성 테스트가 통과했다는 사실만으로 위 *수동 예약* 경로까지 안전하다고 단정하지 말 것. 실제 재현에 성공/실패 여부를 로그로 남겨라.

### 2.2 수정 계약

- 작업의 적법한 **실제 예약 시작 시각** 이전 시간은 절대로 처리량으로 적립하지 않는다. 시계는 권위 있는 게임 `settledTick`과 일치해야 한다.
- `0 → 양수` 처리능력 연결, 오랫동안 정지한 뒤 예약, 취소 후 재예약, 일시 OFF/ON, 저장/불러오기, 시계 분할 진행, 처리능력 변경을 모두 다뤄라.
- 해결책은 코드 구조를 조사해 선택하되, 작업 시작시각 기록/권위 있는 현재시각 앵커 또는 무작업 시각 동기화 등으로 **수동·자동 두 경로 모두** 보호해야 한다. 낮은 수준의 API가 게임의 현재시각을 모른다면 임의로 0시각을 가정해 이미 지난 시간을 공짜 처리하는 대신 명시적 시각 계약을 둬라.
- 시간 역행, 미래 시각 위조, 유효하지 않은 예약, 중복 작업을 명시 거부. 실행 순서/FPS/시간 분할에 따른 결과가 일치해야 한다.
- 매 시간 모든 천체의 포장 원장을 불필요하게 깊은 복제·전체 검증하여 성능을 심각하게 떨어뜨리는 방식은 피한다.
- 기존 예약 소재/C/Wh 보호, 전량 작업 완료 시점의 회수·비용, 취소 시 escrow 반환 규칙 유지.

## 3. B — 광석 4SCU/U의 실제 현지 포장·개봉 [핵심 추가]

### 3.1 배경 및 구현 경계

현재 PR #12는 `quoteIndustryCargoSCU(ore)`로 물리/소재 견적은 계산하지만 `quoteIndustryContainerPack()`에서 `blocked-ore-lot-adapter`로 실포장을 막는다. 이것은 단위가 아니라 **광석 품질/출처 로트가 `industry-runtime`의 `inventoryLots` 및 `planetInventory[...].ore[low/medium/high]`에 따로 남아 있기 때문**이다.

이번 패치에서는 같은 행성/소유자의 **명시적 광석 포장 → 현지 봉인 보관 → 정수 컨테이너 개봉 → 원래 품질 로트 복원 → 제련 투입**을 가능하게 한다. 이것은 **실제 행성 간 배송을 구현하라는 요구가 아니다.** 수송 중/타 천체 인도에 필요한 로트 이전 어댑터가 없다면 그 경로는 계속 fail closed로 두어라.

### 3.2 필수 로트 정보와 원장

기존 광석 로트의 필드를 손실 없이 보존할 것:

`bodyId`, `ownerId`, `depositKey`, `depositId`, `grade`(`low/medium/high`), `processingDifficulty`, `amountQ`.

- 원래 원광 재고와 원천은 `inventoryLots`, `planetInventory[body][owner].ore`, `oreRemaining`, `oreExtracted`, `materialLedger`로 관리된다. 포장한다고 광석을 새로 채굴하거나 품질을 재추첨하지 말 것.
- 포장에는 **사용자가 선택한 로트(또는 명시한 선택 정책에 따라 결정적으로 정렬된 실제 로트)** 에서 `amountQ`만 차감. 개봉 시 **같은 출처·등급·난도**로 정확히 복원. 재고 잔량이 부족하거나 출처가 불분명하면 전체 거부.
- 기존 미포장 광석은 제련이 직접 사용 가능하지만, 봉인된 광석은 **개봉 전에는 제련의 가용 원광으로 잡지 말 것**. `inv.ore`가 실제 제련 가능한 품질별 자유 재고인지, 총 소유량인지를 명확히 분리해 이중 계수 방지. 기존 UI에 필요한 경우 자유/봉인/전체를 구별해 표시.
- 여러 광맥/품질의 로트를 같은 규격 컨테이너에 넣는다면 실제 적재 내역(`lotManifest`)을 합계와 함께 보존해야 한다. **서로 다른 로트의 컨테이너를 단순히 `resourceId|specId|fillQ`만 같다고 합쳐서 출처를 지우면 안 됨.** 동일 내용·로트 구성이 완전히 같은 그룹만 집계하거나, 로트별 집계/별도 검증 가능한 명세를 사용한다. 개별 상자 오브젝트 양산 금지.
- 컨테이너 일부만 개봉하거나 일부 광석을 소비한다면 **개봉한 정수 컨테이너 전체의 로트 조성**과 남은 광석의 로트 조성을 일관되게 처리해야 한다. 일부 내용물에 비례하여 포장재를 무료 회수하거나 남은 광석을 등급 없는 generic ore로 버퍼링하지 않는다.
- 복수 로트 합포장/부분 개봉을 일괄 지원하기 어려우면 **이 작업에서 지원하지 않는 조합을 명확하게 fail closed** 처리하고 제한을 문서에 공개한다. 그 대신 지원하는 단일 로트·전체 컨테이너 경로는 실제로 동작하고 검증되어야 한다. 물리 견적만 지원하는 상태로 '광석 실포장 완료'라고 주장하지 말 것.

### 3.3 원자성·정합성 (가장 중요)

- 광석은 기존 `packagingAccount.freeQ.ore`에 임의로 추가하는 편법으로 해결하지 않는다. 기존 산업 로트 재고와 SCU 포장 원장을 **하나의 검증/커밋 경계**에서 갱신해 중간 실패 시 둘 다 원상복구해야 한다.
- `quote`는 저장 상태를 바꾸지 않고, `commit`은 수량·로트·원장 revision·규격/해금·C/전력·시각/소유자 정보를 재검증한다. 다른 상태의 견적 재사용/위조/중복 커밋 차단.
- 동일 자원인 합금 내용물과 합금 포장재는 계속 **별도** 차감. 광석 내용물 8U라면 32SCU 포장재 합금 **0.450U**, 수취 개봉 시 구조재 **0.405U 회수/0.045U 손실**이 원칙. 광석은 소모/개봉 전후 양이 바뀌지 않아야 함.
- 용기 구조재는 실제 현지 합금 자유재고에서 소비. C/Wh가 null이면 **광석도 견적만 가능하고 실제 실행 보류**. 오직 명시적 비용/전력·실제 재고를 주입한 테스트 규격만 포장 실행 가능.
- 포장/개봉/자동화가 광석의 `quality lot`을 훼손하지 않고, 생산·소비·추출 장부와 연속 보존식을 만족해야 함. 산업 validator가 봉인 광석을 무시하거나 옛 v1 projection을 이용해 허위 합격 처리하지 않도록 엄격한 전체 보존 검증 추가.
- 행성·소유자/광맥의 위조, 중복 lot 참조, 다른 지질 프리셋의 `depositKey`, 등급/난도 변조, 총량·컨테이너 개수 불일치, 저장 훼손이 발생하면 **전체 거부**, 원문 격리 및 무료 물질 생성 방지.
- 새 선체 화물창/배송 객체를 만들지 말고, 현지 산업/SCU 장부 어댑터에 국한. 실운송 API의 추상 delivery 확인을 광석의 라이브 순간이동에 재사용 금지.

### 3.4 저장 및 호환

- PR #12의 `industry schemaVersion:3`, `packaging book schemaVersion:2` 및 엄격한 v1/v2→v3 절차를 우선 점검한다.
- 실제 새 필드가 필요한 경우 기존 상태를 **검증한 후** 최소 이관 경로와 원본 보존·안전 실패 정책을 추가한다. 필요 없는데 거대 세이브 이관·불필요한 version 증가를 만들지 말 것. 새 스키마를 사용한다면 이전 PR #12의 정상 v3 파일을 명시적으로 읽는 경로를 제공하고, 알 수 없는/변조된 필드는 거부.
- 재로드 후 로트 manifest·봉인 재고·묶인 소재·회수 잔여·자동 작업의 시각/예약이 동일해야 한다. 개발용 transient, 자동 저장/복원 OFF, 리프레시 초기화, 명시적인 JSON 내보내기·불러오기, 이관 실패 시 정상 state 미노출 유지.

## 4. C — 회귀검증과 요구 테스트

최소 다음 **행동 케이스**를 새 자동 테스트로 추가하고 재현 가능한 원시 로그를 제출할 것. 검증 가능하면 테스트명에 상황을 드러낼 것. 숫자를 채우기 위한 중복 테스트 금지.

### 자동화 시계

- 500일 무작업 → 처리능력 늦게 연결 → **수동 32SCU 재포장 예약** → 1시간 뒤 8SCU만 처리.
- 같은 조건에서 자동 modernize 예약은 1시간 뒤 최초 정상 처리. 이미 존재하는 테스트도 보존.
- 중도 OFF/ON, 취소·재예약, 1회 4시간 vs 1시간×4, 저장/불러오기, 시계 역행·임의 과거/미래 시각 거부.
- 늦게 연결한 여러 행성/소유자에서 시계가 서로 누수하지 않음.

### 광석 로트·SCU

- 실제 개발 fixture에서 채굴된 **low/medium/high**와 광맥 출처/난도 정보로 8U=32SCU 포장 견적, 봉인, 개봉, 동일 로트 복원.
- **광석 8U** 포장에 합금 0.450U 별도 차감, 개봉 후 0.405U 회수·0.045U 손실. 원광 8U는 보존.
- 0.001U 부분 적재 시 최소 1SCU 컨테이너 전체 비용, 실제 개봉한 정수 용기만 회수.
- 같은 등급의 서로 다른 광맥, 다른 등급의 혼합 요청이 **정보 보존 가능한 방식으로 처리**되거나 위험한 조합만 명시 거부.
- 봉인 광석으로는 제련 불가, 합법적인 개봉 후에는 원래 품질 수율 14/33/52%로 소비. 광맥 잔량/채굴 내역 불변.
- 재고·합금·C·Wh 부족, 잘못된 로트/소유자/출처, 컨테이너 그룹 변조, 낡은/수정된 견적, 중복 적용 시 모든 관련 상태 byte-for-byte 또는 구조 비교 기준 불변.
- 새 규격 세대 해금만으로 과거 로트/소재 소급 변화 없음. 이전 산업·컨테이너 수소/합금 운용 결과 불변.
- 물질 장부: 원광(미포장+봉인+합법적 현지 잔여+정상 제련 소비), 합금(자유+포장재+회수+손실+소비), C, 전력에서 중복 생성·소멸 없음.
- 실제 천체 간 운송 엔진 없이 타 천체 광석 수송/인도/개봉을 이미 된 것처럼 허용하지 않음. `inTransit` 목적지 선반영 없음.

### 기존 기능·브라우저·성능

## 5. 변경 파일 및 보존 범위

먼저 실제 호출 관계를 검색하여 바뀔 필요가 있는 파일만 수정. 주 예상 대상:

`dist/src/resource-definitions.js`의 4SCU/U를 다시 1SCU/U로 바꾸지 말고, 공식 천체/인구/지질/경제 1~3차 원시 모델·입력·결과, 이전 PR #11/#12 보고서·원본 보존 데이터를 수정하지 않는다. 필요한 허용 기존 파일 목록은 **기준 PR #12 HEAD에 대한 새 보존 manifest**로 별도 작성·검증. 과거 보호 manifest를 결과에 맞춰 재작성하여 은폐하지 않는다.
