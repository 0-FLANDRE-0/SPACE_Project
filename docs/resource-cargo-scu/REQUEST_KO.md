## 0. 우선순위와 이전 지시서와의 관계

이 문서는 선행 `RESOURCE-UNIT-1 + PACKAGING-1`의 **개정 계약**이다. 특히 이전 문서의 **「1U = 화물 공간 1U」「화물 용량은 U 하나」「자원별 공간 환산 금지」「벌크 자원은 포장 불가능」「수소만 패키지형」** 등의 내용은 더 이상 적용하지 않는다. 선행 구현이 잘못됐다는 뜻이 아니라 게임 설계가 변경된 것이다. 새 설계에 맞춰 필요한 부분만 리팩터링한다.

- **U:** 경제 생산·소비·거래·재고의 자원 수량. 기존 숫자와 건설/산업 수율은 변경하지 않는다.
- **SCU (Standard Cargo Unit):** 저장·운송에 쓰이는 공간 용량과 **표준 운송 컨테이너 크기**. 자원별 `SCU/U` 환산이 존재한다. **제3의 추상 화물 단위를 만들지 말 것.**
- **m³:** SCU 외형을 설명하는 SI 물리 메타데이터. 평소 게임 자원·물류 UI에 별도의 m³ 화물 수량을 강요하지 않는다.
- **컨테이너:** 재고 독립 상품 또는 빈 상자 자산이 **아님**. 내용물과 묶인 포장 소재를 갖는 일시적 운송 포장 상태다. 포장 해제 시 원래 포장에 실제 투입했던 소재를 기준으로 일부 회수하고 나머지는 손실 처리한다. 새로 포장하려면 그 소재를 다시 준비해야 한다.
- **C 및 전력:** 컨테이너 제작·충전·검사·하역·냉각 등의 세부 비용은 **ECON-SIM-4에서 탐색·결정**한다. 지금은 견적 필드/API만 두고 미정 비용을 임의의 `0` 또는 공짜 공급으로 치환하지 않는다.

진행 순서: 선행 코드 조사 → SCU 데이터 정의 → 범용 컨테이너 레시피 → 포장·개봉 장부 및 자원별 어댑터 → 컨테이너 조합 견적 → 미래 섹터 물류 경계 계약 → 저장/회귀 테스트 → 한국어 보고.

## 1. 결정된 수치 — 임의 변경 금지

### 1.1 자원 U의 실제 내용물

| 자원 | 1U 내용물 | 1U의 장거리 운송 공간 | 상태 |
|---|---:|---:|---|
| `ore` 광석 | **10,000kg** | **4 SCU** | 공간 계수는 현 단계의 잠정 물류 기준. 광석 종류·벌크 밀도에 따라 후속 물리 검토 가능 |
| `alloy` 합금 | **10,000kg** | **4 SCU** | 현재 물류 기준 |
| `hydrogen` 수소 | **500kg** | **8 SCU** | 현재 물류 기준. 액화수소와 극저온 보관 설비/단열/구조물이 같은 점유 공간에 포함 |
| `residue`, 미래 특수 자원 | 미정 | 미정 | 추측해서 채우지 말 것. 실제 운송 견적은 규격 정의 전 명시적 거부 |
| `credits` | 화폐 C | 없음 | 포장 대상 아님 |

- 합금은 철강·알루미늄·비철금속·특수금속을 포괄하는 **추상 산업 자원**이다. `alloy 1U=10t`를 90t로 올리지 않는다.
- 수소의 8SCU는 순수 수소 500kg 자체의 부피뿐 아니라 **컨테이너/극저온 설비를 포함한 총 외형 점유량**이다. 운송 질량은 수소 500kg + 실제 투입된 포장 소재 질량(+ 추후 확정된 추가 소재)로 계산한다. 무게가 없는 무료 냉각장치/고정 장치 질량을 조용히 invent하지 말 것.
- **화물용량 SCU와 자원 U 수량은 다른 차원**이다. 예: 합금 8U = 32SCU, 수소 4U = 32SCU. 둘 다 32SCU 컨테이너 한 개를 사용할 수 있다는 설정이다. 단, 포장 규격과 안전 조건은 다를 수 있다.
- 이 규칙이 광석의 모든 종류·형태에 대해 물리적으로 가능하다고 인증하지 말 것. 특히 원광 벌크 밀도/실제 내부 체적은 추가 검토 대상으로 기록한다.

### 1.2 SCU의 물리 외형과 표준 컨테이너 크기

**정확한 1SCU 외부 부피**는 `1.25³ = 1.953125m³`이다. UI 표시에서는 약 `1.95m³`라고 반올림해도 되지만, 내부 기하 계산/규격 정의에는 정확한 값을 사용한다.

| 컨테이너 | 표준 외부 치수 (m) | 정확한 외부 부피 (m³) |
|---:|---|---:|
| 1SCU | 1.25 × 1.25 × 1.25 | 1.953125 |
| 2SCU | 2.5 × 1.25 × 1.25 | 3.90625 |
| 4SCU | 2.5 × 2.5 × 1.25 | 7.8125 |
| 8SCU | 2.5 × 2.5 × 2.5 | 15.625 |
| 16SCU | 5 × 2.5 × 2.5 | 31.25 |
| 24SCU | 7.5 × 2.5 × 2.5 | 46.875 |
| 32SCU | 10 × 2.5 × 2.5 | 62.5 |

- 이 치수는 **외부** 규격이며 내부 유효 적재 공간을 100%로 간주한 구조공학적 인증치가 아니다.
- 이번 범위에서는 3D 실제 배치·컨테이너 충돌·화물창 출입구·최대 하중 검사까지 구현하지 않는다. 향후 별도의 질량/가속·하중 제약을 연결할 메타데이터/API만 두면 된다.
- 내용물과 컨테이너 소재는 **포장된 4/8/32SCU를 이중 점유하지 않는다.** 포장 소재는 질량에는 반영한다.

### 1.3 2100년대 표준 범용 컨테이너 소재 레시피 — 이번 작업의 공식 구조 기준

| 규격 | 컨테이너 1개 제작에 필요한 합금 | 합금 kg | 포장 해제 시 소재 회수율 |
|---:|---:|---:|---:|
| 1SCU | 0.025U | 250kg | 90% |
| 2SCU | 0.045U | 450kg | 90% |
| 4SCU | 0.085U | 850kg | 90% |
| 8SCU | 0.160U | 1,600kg | 90% |
| 16SCU | 0.270U | 2,700kg | 90% |
| 24SCU | 0.370U | 3,700kg | 90% |
| 32SCU | 0.450U | 4,500kg | 90% |

**이 표는 소재량·회수율에 대해서만 적용한다.** 과거 테스트 예시인 **8SCU당 합금 0.05U는 폐기된 후보**이므로 공식 새 값에 섞지 않는다. 물질/재료 요구량은 여러 자원 `[{resourceId, amountQ, recoveryRate}]` 레시피로 표현하고, `alloy`만 하드코딩하지 않는다. 향후 특수합금/아스트로지늄 등 복수 소재를 추가할 수 있어야 한다.

참고: 32SCU 1개로 합금 8U(80t)를 수송할 때 포장 합금 0.45U(4.5t)를 추가 투입한다. 이건 미래 중량 컨테이너 설정값이며 실제 구조 강도·가속시 하중 인증은 후속 물리 검토다.

### 1.4 회수·소유권 규칙

1. 포장할 때 **내용물 U와 포장 소재 U**를 출발지의 올바른 소유자/천체 재고에서 별도로 차감한다. 동종 재료(합금으로 합금 포장)도 가능해야 한다. 입출력을 원자적으로 처리하고, 내용물을 포장하기 위한 포장재를 다시 포장하는 무한 재귀는 만들지 않는다.
2. 컨테이너/포장 재고에 **실제로 묶인 소재 양**을 기억한다. 규격이 신형으로 바뀌어도 구형의 기존 투입량이 소급 변경되지 않는다.
3. 최종 개봉·사용 시 포장 소재의 **90%를 실제 수취/개봉 소유자의 자유 재고로 회수**, 10%는 물질 손실로 기록한다. 유실/파손률은 나중에 연구·사고로 확장 가능하나 현재는 별도 확률을 임의 도입하지 않는다.
4. **빈 컨테이너 객체·재고·반송·반복 충전 자산은 만들지 않는다.** `회수한 소재로 새 컨테이너를 제작`하는 과정을 추상화한다. 따라서 `재사용 가능`은 독립 빈 컨테이너의 무한 무료 재사용을 뜻하지 않는다.
5. 포장된 화물은 실제 운송 중에도 내용물 및 묶인 소재의 소유권/보존식을 유지한다. 목적지에 도착하지 않았다면 목적지 재고에 미리 더하지 않는다.
6. 포장 기술 연구는 신형 컨테이너 레시피(필요 소재량·회수율·C·전력·안전 조건)를 해금한다. 구형 패키지 우선 사용·여유 자원을 이용한 자동 개선·소비 직전 구형의 불필요한 재포장 회피 원칙을 유지한다. **연구 완료로 기존 소재가 즉시 생성/변환되는 일은 없다.**

## 2. 컨테이너 수와 SCU 환산은 자원량이 아닌 *실제 운송 포장*을 대상으로

- 평소 행성 경제의 원광·합금 재고는 계속 `U`로 표현한다. 생산 즉시 모든 광석/합금을 매번 컨테이너로 포장하지 말 것.
- **장거리 운송 명령**에서 `자원 U × 자원별 SCU/U = 운송에 필요한 SCU`를 계산한다. 물질과 함께 가져가는 패키징 소재는 같은 SCU 내부에 포함한다.
- 포장 컨테이너는 1/2/4/8/16/24/32SCU의 **규격별 집계 수량**으로 표현하고, 소재비는 컨테이너 **한 개당 한 번** 부과한다. 무슨 자원이든 포장 비용을 `U당 합금 X`로만 계산하지 않는다.
- 일부만 채운 컨테이너도 **외형 용량 전체 SCU**를 차지하며 **한 개당 전체 제작 소재**를 지불한다. 불필요한 대형 컨테이너 선택은 불리해야 한다.
- 같은 자원이라면 규격별 묶음을 집계하고, 다른 자원 혼합 적재는 이번 단계에서 필수가 아니다. 기본은 **단일 자원별 컨테이너**로 구현해도 된다. 혼합 화물/복잡한 선적은 후속 물류 단계.
- `resourceId`가 alloy인 경우 `contentsQ`와 `bondedMaterialsQ.alloy`를 별도 회계로 관리한다. 예: **합금 8U를 32SCU 한 개에 포장하려면 자유 합금 8.45U**가 있어야 하며, 개봉하면 합금 내용물 8U와 회수 0.405U, 손실 0.045U가 남는다.
- `0.001U` 같은 아주 작은 수량도 취급하되, 표준 컨테이너 최소 1SCU의 실물 비용을 공짜로 만들지 말 것. 부분 적재와 정수 Q 및 회수 잔여 누적을 보존한다.
- 일반 산업 시설의 **직접 원료 공급/사용**은 기존 실제 로트/질량/품질을 유지하고 운송 포장만 중복 부과하지 않는다.

### 2.1 규격별 조합 자동 견적의 경제 원칙

**동일한 화물에 대해 대형 컨테이너는 충분히 채울 수 있다면 소형 다수를 쓰는 것보다 자재·취급 측면에서 유리**해야 한다.

| 동일 32SCU 용량 조합 | 필요한 합금 | 90% 회수 이후 합금 손실 |
|---|---:|---:|
| 4SCU × 8개 | 0.680U | 0.068U |
| 8SCU × 4개 | 0.640U | 0.064U |
| 16SCU × 2개 | 0.540U | 0.054U |
| 24SCU + 8SCU | 0.530U | 0.053U |
| **32SCU × 1개** | **0.450U** | **0.045U** |

- 포장 견적은 *필요 SCU, 표준 컨테이너 수/규격 조합, 전체 투입 소재별 U, 회수 예상량, 최소 SCU 낭비량, 후속 C/전력 자리*를 반환.
- **현 단계의 기본 자동 선택 목표는 소재(합금 등) 투입량 최소화**. 동률이면 점유 SCU/빈 공간 최소, 그다음 컨테이너 개수 최소, 마지막은 안정적인 규격 순서 등 결정적 타이브레이크. 단, C/전력이 미정일 때 이를 포함해 `완전한 총비용 최적화`를 완료했다고 주장하지 말 것. ECON-SIM-4에서 각 재료의 시장가와 C/전력/물류 취급비가 정해지면 그 값으로 객관함수를 교체할 수 있게 하라.
- 정수 Q 및 SCU 수량 계산에서 무제한 공간/엄청난 컨테이너 생성으로 시간·메모리가 폭증하지 않도록 할 것. 동적 계획/집계 방식 등을 사용하되 **큰 것부터 무조건 채우는 탐욕 알고리즘이 늘 최적이라고 단언하지 말 것.** 적은 SCU에는 전수 검증, 큰 물량은 효율적인 집계와 결정적 결과를 제공할 것.
- 실제 화물창 적재 제한·특정 규격 컨테이너 취급 불가/기술 해금 제약을 차후 `allowedContainerSizes` 등으로 주입할 수 있게 하라. 이번에 함선 3D 컨테이너 배치 알고리즘은 만들지 않는다.

## 3. 산업용 보관과 장거리 운송 포장을 구분하여 **이중 포장비** 방지

**중요:** 기존 수소는 처음부터 `hydrogen` 포장 묶음으로 관리되며 `hydrogen-legacy-unpriced-v1` 호환 규격이 존재한다. 새 SCU 물류 포장이 추가됐다고 수소를 포장할 때마다 무조건 소재를 두 번 차감하지 마라.

- 수소 1U=500kg + 8SCU에 맞는 **극저온 보관/단열 설비를 포함한 상태**라는 설정을 유지한다.
- 직접 연결된 인접 섹터의 수소 이동은 배관/전용 취급망으로 처리할 수 있어 **별도의 SCU 운송 컨테이너 제작**을 강제하지 않는다. 그렇다고 냉각·보관 자체가 무료이거나 수소가 일반 환경에서 무손실로 존재한다는 뜻은 아니다. 실제 기초 냉각·보관 C/전력은 ECON-SIM-4/후속 산업 시스템의 비용 경계에서 다룬다.
- 동일 자원을 이미 규격에 맞게 포장했으면 운송 시 다시 포장재를 이중 부과하지 않는다. 컨테이너 호환 여부를 확인하고, 호환 불가 시에만 원자적 재포장을 견적한다.
- 기존 `hydrogen-legacy-unpriced-v1`을 소재가 들어 있는 유료 8SCU 포장과 **거짓으로 동일 취급하지 않는다**. 구형 미가격화 수소의 실제 묶인 소재는 0이며 개봉해도 합금 회수 0. 운송 시 필요한 정식 컨테이너는 적법한 별도 포장/전환을 거쳐야 한다. 신규 확정값 없이 무료 유료 컨테이너로 업그레이드하지 말 것.
- H 포장 내 냉각장치의 소재비를 일반 컨테이너 구조재 + 특수 설비 요구 재료/C/전력으로 **데이터 기반 확장**할 수 있게 한다. 현재 추가 특수 자원의 종류·양은 확정하지 않는다.
- 포장을 풀어 수소가 일반 자유 재고로 풀리는 상황에는 *현지 탱크/시설 소비자/배관 등 수소를 받을 합법적 보관·소비 경로*가 필요하다. 이번에는 수소의 자유 재고를 무제한·무손실로 만드는 본체 통합을 하지 않는다. 외부 목적지가 없는 '무료 언패키징'을 신설하지 말 것.

## 4. 장거리·인접 섹터 운송 면제 규칙 — **실제 이동 구현은 다음 단계**

미래 섹터간 물류 API에 명확한 계약을 만들고 단위 테스트를 추가하라. 이번에 육상/우주 물류 AI, 경로탐색, 트럭/셔틀/함선 배치, 실제 섹터 이동을 구현하라는 뜻은 아니다.

| 출발지→목적지 | SCU 컨테이너 운송 포장 | 원칙 |
|---|---|---|
| 같은 섹터 내부 | 면제 | 시설 간 직접 인도 |
| 인접한 섹터(육각 격자 1링) | **연결된 지역 공급망이 있을 때 면제** | 배관·도로·지역 운송 수단. 운송 시간/C는 여전히 발생 가능 |
| 2링 이상 떨어진 섹터 | 필수 | 장거리 표준 컨테이너 |
| 서로 다른 행성/위성 | 필수 | 천체 간 SCU 포장 운송 |

- `same-sector` 또는 `adjacent-connected` 등의 조건으로 추상적인 `requiresSCUPackaging(...)` 순수 함수를 제공. 인접은 **실제 육각 격자 이웃 관계**(행성 구형 격자 시스템의 연결 그래프)를 확인하는 계약으로 정의. 인접이더라도 지역 공급망이 없으면 면제하지 않는다.
- 면제 판단은 **화물의 원래 출발지와 최종 목적지**, 목적지의 연속적 인도 계약을 기준으로 한다. A→D 장거리 운송을 A→B→C→D 인접 1링 여러 개로 자동 분할해 컨테이너 비용을 0으로 회피하지 않도록 shipment ID/ultimateDestination 등을 받을 확장 지점을 둔다. 실제 중간 환적/다른 배송 명령에는 합당한 시간·취급비가 들도록 설계상 분리.
- **인접 = 무상/순간이동이 아님.** 포장 소재비 면제와 운송 자체의 연료/시간/운임은 다르다.
- 기존 `transferPackagedResource`는 원장 계정 이전 도구일 뿐, **행성 간 즉시 배송이 구현됐다는 뜻으로 UI에 노출하거나 실제 우주 물류라고 포장하지 말 것.** 실제 출발 차감 → 화물 운송 중 예약/보관 → 도착 후 인도/개봉 원자성은 후속 물류 단계에 연결할 계약/테스트 설계로 남긴다. 적어도 미래 API가 `inTransit`과 행성 재고를 혼동하지 않게 정의하라.

## 5. 코드에서 반드시 바꿔야 하는 실물 충돌 지점

현재 확인한 선행 PR #11 파일:

1. `dist/src/resource-definitions.js`
   - `cargoUnitsPerU === 1`을 강제하는 `ResourceRegistry.set`, 단순 `sum(U)`인 `cargoQuantityU`는 새 SCU 설계와 충돌.
   - `cargoSCUPerU` 같은 자원별 데이터 항목과 `quoteCargoSCU`, `resourceCargoSCU` 등 SCU 전용 API로 분리. 기존 함수는 **의미를 모르게 바꿔 사용하지 말고** 호출처 검색 후 명시적으로 변경/대체. 미정 자원은 잘못된 환산 없이 거부. 화폐 C는 화물 공간 대상이 아님.
2. `dist/src/packaging-specs.js`
   - 지금의 `PackageRegistry`는 `resourceId` 중심이고 `m.resourceId === s.resourceId`를 거부한다. 이 상태로는 **합금 → 합금 컨테이너** 포장이 불가능.
   - **컨테이너 규격(크기·형상·기본 제작 소재 레시피)과 내용물 자원/패키징 기술 세대**를 분리하라. `containerSpecId`, `resourceId`, `generation`, 필요 시 운송/특수 보관 유형을 합성하는 구조. 컨테이너 소재 레시피와 내용물은 분리된 계정이며 무한 재귀 포장은 금지. 단순히 자기참조 검사를 전부 없애고 끝내지 말 것.
   - 기존 `hydrogen-legacy-unpriced-v1`의 과거 투입 소재 0 보존.
3. `dist/src/packaging-inventory.js`, `packaging-automation.js`
   - `groups[specId]`, `bondedMaterialsQ`, `counters`, 회수 잔여를 새 `container size/quantity` 구분과 일치시켜라. 개별 컨테이너 객체 수십만 개 대신 **규격별 묶음/컨테이너 개수**로 집계한다.
   - 컨테이너당 한 번 비용 부과, 같은 내용물/소재 동시 출입, 일부 적재/부분 소비, 구형 우선, 자동 재포장/취소/예약/원자성, 타 계정 이동 시 소재 보존을 테스트한다.
   - 부분 수요가 컨테이너를 개봉할 때 실제 회수 가능한 소재를 정확히 계산하라. 현장 소비에서 컨테이너 일부만 열린 것처럼 소재를 공짜로 비례 반환하지 말고, **개봉할 실제 컨테이너 수를 기준으로 회수**하라. 나머지 내용물은 현지 재고로 풀거나 안전한 보관 위치로 이전해 연속 소비를 지원한다. 수소 등의 보관 요구를 우회하지 않는다.
   - 회수율 90%에서 0.001U 정수 Q 때문에 즉시 소수 Q가 생기면 **반올림 잔여 누적**으로 보존하고 전체 회수율/실제 손실/부담이 서로 모순되지 않게 한다.
4. `dist/src/industry-packaging.js`, `industry-runtime.js`, `industry-storage.js`, `industry-fixture.js`
   - 광업 부산물, 제련, 건설, 원광 품질 lot, 유한 광맥/수소 원천, 개발 시험 초기 재고의 수량·시계·조건을 그대로 보존.
   - 광석 lot/품질을 잃어버리고 generic free ore에 넣지 마라. 운송 포장 시 lot별 메타데이터(광맥 출처·품질·가공 난도)를 유지할 수 있는 어댑터를 만들거나, **이번 범위에서 해당 상품에 대한 실운송 포장을 fail closed로 명시적 보류**. 모든 자원에 대한 견적·레시피 API 지원과 모든 자원의 실제 live 산업 배송 구현은 서로 다름.

5. UI
   - 기존 산업 패널과 모바일 레이아웃, 기본 재고 U 표기를 유지. 화물 견적 상세에서만 SCU 합계·컨테이너 조합·소재 투입·회수 예상량 등을 표시할 수 있는 **확장 지점** 마련. 지금 새 물류 화면·컨테이너 관리 화면을 만들지 않는다.

## 6. 비용 미정 상황에서의 실행 정책 — 엄격

- 위 표의 **합금 제작량 및 90% 회수율은 구조적 게임 설계값으로 적용**해도 된다. 다만 직접 포장 C/전력과 극저온 추가 C/전력은 **미결정**이다.
- 컨테이너 레시피에는 `directCostCPerContainer`, `electricityKWhPerContainer`, 필요 시 `loadingHandlingC`, `cryogenic...` 등 **후속 매개변수/비용 경계**를 둔다. 항목이 없거나 `null`이면 **미결정**이다. `0`은 명시적인 0원/0kWh와 반드시 구분한다.
- 견적 API는 **결정된 물리량·소재 투입·90% 회수** 부분만 산출하고 `status:'pending-cost-input'`처럼 집행 보류를 명시할 수 있다. 이를 사용해 테스트·미래 UI에서 포장 요구량을 확인한다.
- 비용이 `null`인 상태에서 실제 정식 유료 운송 포장 거래를 **무료로 확정·커밋하지 말 것**. 원자적 실제 거래 테스트에는 테스트 전용으로 C/전력 값을 명시적으로 주입하여 검증한다. 테스트용 숫자가 공식 게임의 정식 비용으로 채택된 것처럼 쓰지 않는다.
- 과거의 미가격화 `hydrogen-legacy`는 현재 산업 기존 동작을 유지하기 위한 **명시적 호환 경로**로만 유지한다. 새 장거리 운송을 공짜로 허용하는 정식 레시피가 되어서는 안 된다.
- 수소 시장가격 `0.4C/U`, 제안가격 `1.2C/U`는 ECON-SIM-4의 **비교 후보**다. 이번 작업에서 어느 것도 확정하지 말 것.

## 7. 자동 세대교체는 계속 유지하되, 자동 컨테이너 조합과 구분

- **자동 컨테이너 조합:** 새로운 장거리 수송을 준비할 때 가능한 규격 크기 중 소재 사용량과 포장 부담을 최적화해 선택하는 절차. 연구가 없어도 수행.
- **자동 패키징 현대화:** 오래된 기술 세대의 재고를 여유 C/전력/소재/설비 능력에 따라 점진적으로 신형으로 바꾸는 절차. 연구/설비/비용이 미연결이면 계속 안전 대기. 두 동작을 하나의 버튼이나 함수로 대충 뭉치지 말 것.
- 오래된 포장 규격부터 소비하고, 신규 컨테이너 제작은 해금된 최신 승인 세대의 레시피를 사용. 기술 해금 즉시 기존 재고의 결합 소재와 회수율을 소급 갱신하지 말 것.
- 1세대 컨테이너 제작 비용이 이미 투입됐는데 재포장 과정에서 회수 전액+새 소재 전액을 계산하지 않은 채 소재가 생기지 않게 하라.

## 8. 테스트/검증 필수 사례

테스트는 최소한 다음 계약을 다뤄야 한다. 단순 출력 스냅샷만 검증하지 말고 재고/장부의 원자성·보존식을 대조하라.

### 8.1 물리·데이터

- `1SCU = 1.953125m³` 정확도와 1·2·4·8·16·24·32SCU 컨테이너의 치수/부피 확인.
- 합금/광석 10,000kg/U, 수소 500kg/U 보존. 합금 8U=32SCU, 수소 4U=32SCU; 100SCU 창고에 32+32+36은 허용, 32+32+37은 거부.
- 자원 SCU/U 미정·화폐·음수·0.001U 경계·잘못된 규격/자기 참조·여러 소재 참조 시 fail closed.

### 8.2 컨테이너 제작·소재 보존

- 32SCU × 1: **합금 0.450U 투입**. 90% 개봉 회수는 0.405U, 손실 0.045U.
- 동일 32SCU를 4SCU × 8로 운송할 경우: 합금 0.680U 투입, 회수 0.612U, 손실 0.068U. 반드시 32SCU 1개가 소재 기준 유리.
- 동일 32SCU를 8SCU × 4로 운송: 0.640U 투입. 16SCU × 2는 0.540U, 24+8은 0.530U. 자동 조합이 동일 목적/허용 크기에서 비효율 선택을 하지 않음.
- 합금 내용물 8U를 32SCU에 포장: 자유 합금 **8.450U 차감** → 목적지 개봉 시 합금 8U + 회수 0.405U = 8.405U 도착, 손실 0.045U. 이전 출발지에서 회수 소재가 중복 생성되지 않음.
- 포장 소재가 `alloy` 이외의 신규 자원 여러 개로 구성될 수 있음. 내용물과 소재 자원 ID가 같아도 무한 재귀/허위 차감 금지.
- 부분 적재가득 채운 컨테이너와 달리 전액 제작 소재를 냄. 부분 개봉 때 실제 열린 컨테이너 수에 맞춰 회수하며, 0.001U 반복 작업과 일괄 작업 간 물질 보존/잔여가 합치도록 검증.
- C·전력 입력 미정 때 견적은 나올 수 있지만 실제 유료 거래는 중단. 가상 테스트 C·전력 값과 실제 재고를 공급한 경우에만 원자적 커밋.

### 8.3 재고/자동화/산업 회귀

- 구형/신형 세대 동시 존재, 구형 우선 소비, 최신 규격 생산, 자동 개선이 미정 비용·재고 부족·처리능력 부족 시 보류, 예약/취소/시간 분할 불변.
- 원광의 출처·품질 lot, 제련 수율 14/33/52%, 광업/제련 건설비·월 처리량, 수소 생산100U/월/제련85U/월 상한, 핵융합2.5U/월의 계약을 임의 변경하지 않는다.
- 현행 개발 fixture 및 transient/새로고침 초기화, 기존 산업 패널 PC/모바일 회귀.
- 손상 저장·중복 포장·원격 소유권 회수·미도착 재고 즉시 반영·부족 자원 중간차감/부정 견적 재사용을 거부.
- `requiresSCUPackaging`: 동일 섹터/인접 연결 시 면제, 2칸 이상/다른 천체는 필수, 2칸을 인접 1칸씩 나눠 무상 처리하지 않음(최종 목적지 기준).

### 8.4 회귀 명령

```bash
npm run check
npm test
# 선행 PR #11의 보존·게임 산업 브라우저 회귀도 적절히 조정·실행
node scripts/verify-resource-unit-preservation.mjs

```

- `verify-resource-unit-preservation.mjs`는 선행 PR #11 기준의 **그 당시 보존 검사**이므로 이번에 합법적으로 변경된 파일까지 바이트 동일하다고 주장하지 마라. **기존 ECON-SIM-1·2·3의 데이터·소스·원시 산출물 보존**이라는 목적을 유지하되 변경 허용 목록을 정확히 기록/검증하라. 과거 결과/후보/검증 통과 여부를 새 SCU 모델로 재승인하지 않는다.
- 테스트 로그/브라우저 회귀(가능 범위)/미실행 사유를 보고하고, 누락·실패·skip을 숨기지 말 것. 새 SCU 최적화가 큰 화물에서도 비정상적으로 느리지 않은지 성능 보고.

## 핵심 수락 기준 요약

**U는 자원 수량, SCU는 운송·보관 공간.** 컨테이너는 1/2/4/8/16/24/32SCU, 대형 컨테이너가 충분한 물량을 실을 때 소재 효율이 높다. 모든 자원의 장거리 운송에는 컨테이너가 필요하고, 같은 섹터·연결된 인접 섹터의 지역 직접 운송은 예외다. 포장재는 최초에 자원을 실제 차감하여 묶고, 개봉 시 실제 묶은 소재의 90%만 회수한다. **빈 컨테이너는 독립적으로 관리하지 않는다.** 경제적인 C·전력 비용은 ECON-SIM-4에서 결정하고, 그전에는 비용을 무료로 가장하지 않는다. **기존 산업·지질·ECON1~3의 수량과 결과를 보존한다.**
