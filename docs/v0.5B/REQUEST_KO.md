## 1. 핵심 개념: '광역 표면 섹터'

행성 표면의 각 셀은 **광역 탐사·개척·건설·도시화·인구·향후 행성전의 관리 단위**이다. 시설 하나당 셀 하나가 아니라 **한 셀 안에 여러 도시, 광산, 산업시설, 우주항, 군사 시설**이 존재할 수 있는 구조로 설계한다.

- 육지 = 건설 가능 / 바다 = 건설 불가능 같은 이분법 금지. 해양 섹터에서도 해상·해저 시설 가능.
- 가스 행성 역시 같은 방식으로 섹터를 갖지만 **정규 지표면이 아니라 기준 대기층의 광역 관리 구역**으로 해석. 대기 채집/부유 시설 등 가능한 시설 종류는 훗날 환경 규칙으로 제한.
- 지구·화성·금성만 구현하고 거대 행성이나 시험계는 빈 껍데기로 남기는 행위 금지.
- `Planet Size`는 현행 **게임 내 월드 표시 지름** 규칙도 계속 담당한다. 임의 변경 금지.
- 표면 타일 밀도는 `Planet Size`를 **적도를 한 바퀴 따라 지나가는 섹터 수의 목표값**으로 이용한다. 지구 `Planet Size 15`는 약 15칸 목표이지 정확히 15개 강제가 아니다.
- 표면 격자는 고정된 로컬 지리 좌표에 붙으며 행성의 자전과 공전에 함께 움직인다. 표면 ID는 영구 유지.

## 2. 구면 격자의 생성과 데이터 계약

### 2.1 형식

정이십면체를 주파수 `f`로 세분화한 삼각망의 **구면 쌍대(Voronoi/dual)**를 이용한다.

- 원래 메시의 12개 정점 → **오각형 12개**.
- 기타 정점 → 육각형.
- 전체 타일 수 `10 × f² + 2`, 육각형 `10 × (f² − 1)`.
- 예: `f = 2` → 42타일(12+30), `f = 3` → **92타일(12+80)**, `f = 4` → 162타일, `f = 5` → 252타일.
- **지구 첫 검증 기준은 `f = 3`, 92개 광역 섹터.** 기존 UI와 자전/텍스처 위치를 보존해야 한다.
- 오각형 12개에 대해 5개 이웃, 육각형은 6개 이웃을 정확히 생성한다. 외곽 구멍·중복·역면 타일·반대편 선택·공유 변 틈새가 없어야 한다.

정확한 구면 타일 경계와 선택 경계가 일치해야 한다. 렌더링에는 한 다각형, 히트 테스트에는 일치하지 않는 최근접점 대체법을 혼용하지 않는다. 구면 Voronoi 꼭짓점/엣지 생성과 선분 분할을 안정적으로 구현하고, 수치 오차와 폴/날짜변경선(seam) 처리를 검사한다. 3D 단위 구 좌표로 계산하면 위도/경도 seam에 의존하지 않는 편이 좋다.

### 2.2 '모든 행성' 해상도 정책

- 각 행성의 `Planet Size`를 목표 적도 통과 셀 수로 입력한다.
- 지원되는 `f` 후보를 대상으로 **실제 격자와 행성 적도가 교차하는 셀 수**를 샘플링/기하학적으로 평가해 목표와 가까운 `f`를 결정하는 정책을 한 곳에 구현한다. 처음 검증된 지구 `f=3` 매핑은 보호한다.
- **정확히 같은 적도 셀 수를 맞추려고 타일 모양을 비정상적으로 늘리거나 소수점 `f`를 사용하지 않는다.** 실제 계산한 적도 통과 수와 최종 타일 수를 개발자 UI에 표시한다.
- 더 큰 행성의 격자는 자연히 많아져도 된다. 거대 가스 행성의 셀을 인위적으로 92개로 줄이지 않는다. `f` 상한은 기술적 안전 한도로 두고, 상한에 걸린 경우 사용자에게 알려야 한다.
- 생성기의 `orientation/version`을 고정한다. 지구만 임의로 회전시켜 맞추지 않는다. 변경 필요 시 **명시적인 데이터 마이그레이션**을 요구한다.

### 2.3 위성

- `moon` 타입에 `planetSize`가 없다는 이유로 표면 기능을 빼지 않는다.
- 위성은 `satelliteDiameterWorldUnits`, 필요하면 미래의 `surfaceResolutionOverride` 및 자체 해상도 정책으로 타일 수를 결정한다.
- 위성은 작아도 탐사/개발 기능이 필요하므로 실용적인 최소 격자를 지원한다(예: 작은 위성 `f=2` 42개, 확정 밸런스 아님). 위성 타일 ID도 시스템과 위성 ID를 포함한다.
- 위성의 물리/표시 지름이나 모행성 공전 요소를 표면 격자 때문에 변경하지 않는다.

### 2.4 타일 ID 및 재현성

권장 고유 ID 형태:

`{systemId}:{bodyId}:surface:{tileIndex}`

예: `sol:earth:surface:00024` (단, **타일 번호 자체는 실제 생성기의 결정적 인덱싱 결과를 따른다**, 예시 번호에 특정 지리 좌표를 가정하지 않음).

- 시스템 ID, 천체 ID, generatorVersion, `f`, orientation/fingerprint를 저장·검증.
- `tileId`, 정규화된 구면 중심/경계, 5·6개 이웃 ID, 중심의 위도·경도, 면적/면적 비중을 **공용 생성 결과**로 제공.
- 생성 순서의 정렬은 항상 결정적이어야 한다. 같은 seed/정의로 재생성하면 모든 ID·중심·이웃이 동일.
- 입력된 JSON과 다른 generatorVersion, tileCount, gridFingerprint를 조용히 적용하지 않는다. 오류를 표시하고 원본을 보존.
- 향후 행성 표면의 시설·군대·탐사·매장 기록이 이 ID를 참조하므로 릴리스 간 임의 번호 재배정 금지.

## 3. 실제 3D 행성 렌더링과 표면 섹터 선택

현재 `SystemViewer.createBody()`에는 `root -> visual -> axisFrame -> spin -> mesh` 구조가 있다. 지구·행성·위성 텍스처와 자전이 `spin`에 연결된다. 표면 레이어는 **기존 텍스처/자전 프레임에 붙여** 지도와 타일이 일체로 움직이게 한다.

- 기존 구체의 색상·실제 텍스처·구름·대기·토성 고리 및 공전 수식 보존. 새 텍스처를 임의로 갈아엎지 말 것.
- 타일 경계는 실제 표면 위 얇고 반투명한 레이어. 근접 시만 표시하며 멀리서 행성 전체가 철망처럼 보이지 않게 함.
- 지구 구름/대기 투명층을 고려해 Z-fighting 방지. 텍스처/구름이 망가지거나 타일 선이 불필요하게 두껍게 보이지 않아야 함.
- 가스 행성은 명시적으로 **대기 기준 레이어**에 격자를 그리며, 고체 표면이 있다고 묘사하지 않는다.
- 오각형은 일반 셀과 동일한 선택·편집 대상이다. 색과 테두리 형태가 자연스럽게 맞아야 한다.
- 앞면에 있는 타일만 선택한다. 반대편 타일이 관통 선택되거나, 천체 뒤에 격자가 비치는 현상 금지.
- 마우스 클릭·터치·OrbitControls 회전·핀치를 구분. 드래그를 선택으로 해석하지 않음.
- 화면이 작을 때 타일 터치 판정은 모바일 기준으로 조절 가능하되 **인접 셀을 잘못 선택하지 않도록** 검증한다.
- 활성 행성/위성의 표면 레이어만 무겁게 렌더링한다. 다른 항성계의 모든 행성·대형 가스 행성·위성에 항상 수천 개의 개별 Mesh를 생성하는 방식 금지. 타일 경계 배치 렌더링, 필요한 경우 색상 버퍼 재사용/LOD/캐시, 컨텍스트 변경 시 GPU/이벤트 정리.
- 천체 재선택, 시스템 전환, 행성 표면 보기 종료 후 생성 자원 재활용·dispose를 검증.

### 3.1 표면 보기 진입/복귀

기존 천체 선택 시 자동 줌하지 않는 v0.4/0.5A 규칙을 지킨다.

- 천체 선택 정보 패널에, 표면을 가진 **모든 행성/위성**에 대해 `표면 지도` 버튼 추가.
- 버튼을 누를 때만 해당 천체로 부드럽게 접근하여 표면 지도 모드로 진입. `확대` 버튼은 기존 동작 그대로.
- 표면 보기에서도 카메라 회전/확대 및 현재 텍스처 유지. `항성계 지도로 돌아가기` 동작 제공.
- 지구/화성/목성/가상 항성계 행성을 동일한 코드로 여는 것이 핵심.
- 표면 지도에서 셀을 클릭하면 **셀 정보 패널**이 열리고 지도 선택 강조가 유지된다. 선택만으로 카메라가 강제로 점프하지 않는다.
- 표면 모드에서 입력 우선순위: DOM 편집기/정보 패널 > 앞면 표면 타일 > 빈 공간. **항성계 기초 섹터나 행정 편집 입력을 삼키거나 섞지 않는다.** 표면 지도 이탈 시 기존 항성계 모드/선택을 가능한 한 복원.
- 별과 소행성대/비구면 입자 집합에는 `표면 지도` 버튼을 표시하지 않는다.

## 4. 표면 섹터 데이터: 자연지형 + 초기 문명 + 추후 변화

전 행성에 동일하게 적용되는 **버전 있는 공용 스키마**를 설계한다. 특정 지구 ID 분기문으로 인구/자원 UI를 만드는 방식 금지.

### 4.1 '변하지 않는 원본'과 '게임 상태' 분리

1. **Grid Definition**: 지형 격자 생성 버전, 분할 주파수, 로컬 표면 좌표, 이웃관계.
2. **Geology & Environment Template**: 섹터별 자연환경, 육지/해양 비율, 광석/전략자원 **원래 실제 매장지** 및 채굴 난도. 초기 상태라도 탐사 전부터 존재.
3. **Starting Scenario 2100**: 최초 거주·통치 주체, 초깃값 POP·도시화·기반시설, 초기 개발·발견 정보. 게임 시작 연도 2100은 **시나리오 메타데이터**이고, 기존 태양계 천문 epoch를 이 패치에서 강제로 2100으로 이동시키지 않는다.
4. **Future Runtime/Saved State**: 진행 중 인구/시설 변경, 매장량 감소, 탐사 진행률, 군사 점유·피해. **이번 패치에서는 기능을 구현하지 않지만** 분리된 구조의 계약을 문서화한다.

### 4.2 섹터 기본 환경 데이터

- `terrainType`: 육상·해양·혼합·얼음·사막·산악·진공 암석·가스 대기 등 **확장 가능한 카탈로그 기반**.
- `landFraction`/`waterFraction`: 0–1 범위. 암석/해양 행성에서 두 값의 합은 1. **미설정은 `null`**, 자동으로 전부 바다/육지라고 판단하지 말 것.
- `environment`: 온도/방사선/지형 장애/거주 적합성 등의 후속 확장 필드. 아직 측정하지 않은 값은 명시적 미설정.
- `surfaceType`: 고체 지표 / 액체 표면 / 대기 구역 등. **가스 행성은 육지/해양 비율을 강요하지 않는다.** 그 대신 대기권 특성/개발 방식 메타데이터를 편집한다.
- `areaWeight`: 구역마다 면적이 완전히 같지 않을 수 있으므로 향후 인구밀도·산업 규모 산출에 사용할 수 있는 지리적 비중.

### 4.3 자원 단위와 매장량

- **물질 자원 1 U = 10톤**. 금액은 별도 **크레딧 C**이며 U로 환산하지 않는다.
- 기본 원자재는 `ore`(광석), 가공 생산물은 `alloy`(합금). **합금은 매장지가 아니라 제련/생산 자원**이므로 지질 매장지 자원 타입으로 넣지 않는다.
- 일반 광석은 **품질 등급을 세분화하지 않는 공통 자원**으로 시작한다. 희귀 전략자원은 **별도의 매장지/별도의 자원 ID**로 정의한다. 광석 재고를 성분별로 무한히 분리하지 않는다.
- 매장지에는 `depositId`, `resourceId`, `initialReserveU`, 선택적 `extractionDifficulty`, `discoveryTier`, `notes` 등을 갖게 한다.
- 매장량은 유한하며 추후 채굴 시 런타임 `remainingReserveU`가 감소한다. **원본 매장량은 채굴로 덮어쓰지 않는다.**
- 현재는 `ore`를 반드시 지원하고, 전략자원의 ID/정의는 확장 가능한 자원 레지스트리를 통해 연결한다. 미정 자원을 특정 드라이브와 임의로 연결하지 않는다.
- `quantityU`는 유한한 0 이상 숫자; 음수, `NaN`, `Infinity`, 비정상 거대 수 거부. 소수 U 허용(예 0.01 U = 100kg).

### 4.4 시작 시나리오: POP·도시화·시설

- **1 POP = 정확히 1,000,000명**.
- 실제 저장은 비음수 **정수 인구 `populationPersons`**, 화면은 `POP` 단위 환산. 인구가 1,000명인 거주지는 0.001 POP로 표시 가능.
- `urbanizationRate`: 0–1(퍼센트 표시), `infrastructureLevel`: 초기 0–5 등의 프로토타입 구간(카탈로그/후속 조정 가능).
- 인구와 도시화를 현재는 **개별 타일의 초기 상태**로만 수정. 지구 전체 POP은 타일별 값의 합으로 파생한다. 행성 총인구를 별도로 복제 저장하지 않는다.
- 시설은 미래를 위해 `facilities` 배열/종류 ID와 위치(해당 셀)를 지원하도록 스키마 확장점만 마련한다. 실제 생산, 수익, 건설시간은 없음.
- 주민 문명 `civilizationId`, 원칙적 통치 주체 `ownerFactionId`, 향후 실제 점유 세력 `controllerFactionId` 등 필요 시 명시적/선택적 필드로 분리한다. **현재 위치한 항성계 행정 섹터로 소속을 자동 갱신하지 않는다.**
- **지구는 '인류 거주 모행성'이라는 시작 메타데이터**를 가질 수 있지만, 인구 분포·도시화·매장량을 아무 근거 없이 무작위로 확정하지 않는다. 편집기로 사용자가 직접 수치를 설정한다.
- 화성·달의 소규모 식민지는 향후 시작 시나리오에서 편집 가능하게 한다. 사용자 미확정 POP 값을 임의 고정하지 않는다.
- 미입력(`null`, 비어 있음)과 실제 0은 구분. 미개발/미탐사 정보가 있는 타일에 0을 자동 입력해 사실처럼 표시하지 않는다.

### 4.5 미래 탐사와 군사 체계를 위한 데이터 계약만 선반영

- `knowledge`는 진짜 지질 정보와 분리된 **문명별 인지 정보/탐사 진행도** 개념으로 둔다.
- 기초 탐사는 행성 전체 섹터를 훑는다. 정밀 탐사는 **행성 전체 자동 조사**가 기본이고, 특정 섹터를 **우선순위로 지정**할 수 있어야 한다. 작업을 멈춰도 퍼센트/누적 작업량이 유지된다. 상위 센서가 개발되면 기존 조사 기록은 유지하며 새로운 탐사 단계가 열린다.
- 실제 작업 시간(지구형 행성 기준 기초 4–18시간, 정밀 전체 1–2.5일)은 **향후 밸런스**이며 이번 편집기에서 타이머를 돌리지 않는다.
- 군사: 이웃 셀 그래프를 이용한 행성 강습·지역 통제, 표면 좌표를 이용한 궤도폭격·시설 피해·전후 복구에 연결 가능하도록 미래 필드의 의미를 문서화한다. 전투 로직·파괴 이펙트는 절대 구현하지 않는다.

## 5. 범용 개발자 행성 편집기

**지구 전용이 아니다.** 현재 `SystemViewer`에 주입된 모든 지원 대상 행성·위성에서 동일한 편집 UI와 동일한 JSON 스키마로 작동해야 한다.

### 5.1 편집 흐름

1. 브라우저에서 숨겨진 개발자 제스처 또는 `?dev=1`로 개발자 모드 활성화.
2. 항성계의 수성·금성·지구·화성·목성·토성·천왕성·해왕성, 달, 임의 시험계의 별도 행성 중 **한 대상 선택**.
3. 그 대상의 `표면 지도` 진입 → `표면 편집` 버튼 활성화.
4. 터치/마우스로 앞면의 표면 타일 선택 → 편집 패널에 고유 ID·타입·위치·면적·인접 셀·초기 값 표시.
5. 탭 또는 섹션으로 **지형/환경 · 매장 자원 · 초기 인구/도시화 · 기반시설 · 초기 지식 · 향후 시설 메타데이터** 편집.
6. 단일 셀 편집이 먼저 동작해야 하며, 인접 여러 셀 선택과 일괄 적용(예: 도시화율, 지형)은 **후속 또는 여유가 있으면**. 너무 복잡한 편집기의 핵심 기능을 희생하지 말 것.
7. 편집값에 검증 및 `적용`, `취소`, `되돌리기(Undo)` 제공. 잘못된 값은 저장하지 않는다.
8. `JSON 내보내기`, `JSON 가져오기`를 통해 해당 행성의 원본 설정 + 2100년 시작 시나리오를 전송/재적용 가능하게 한다.
9. 다른 행성으로 전환한 후 원래 행성으로 돌아와도 편집값 유지. 저장소 접근이 실패하면 메모리 유지와 명시적 경고.

### 5.2 보기와 편집의 구분

- 일반 플레이어 화면에서는 읽기 전용의 표면 섹터 선택/정보만 표시.
- 개발자 모드에서만 편집 버튼/자원 실매장량/미발견 정보 원본/데이터 가져오기·내보내기가 등장.
- 개발자 전용 데이터가 일반 플레이 정보 패널에 노출되면 안 된다(향후 탐사 시스템에서 미발견 자원 노출 문제 방지).
- **개발자 모드가 숨겨져 있다는 것은 보안이나 인증이 아니다.** 지금은 브라우저의 로컬 편집 도구로 한정. 서버 데이터/다른 플레이어 데이터에 쓰기 금지.
- 기존 행정구역 편집(`AdministrativeRegionUI`)은 별개의 UI. **표면 편집 모드와 행정 셀 편집 모드가 동시에 활성화되면 안 된다.** 화면 전환 시 이전 편집 모드를 안전하게 종료/보존해야 한다.
- 모바일 가로 844×390 및 667×375에서도 지도를 가리는 영구 대형 패널 대신 접고 스크롤 가능한 편집 드로어·탭 사용. 상단/하단의 저장·닫기·전체화면 버튼이 터치 가능해야 함.

### 5.3 모든 행성의 기본값

- 기본 그리드는 해당 천체의 유형과 해상도 정책으로 자동 생성.
- **매장량, 인구, 도시화, 거주 현황 등 사용자 미설정 값은 `null`/미설정으로 보존**. 행성 종류별로 무작위 가짜 POP·광산 데이터 생성 금지.
- 가스 행성은 대기 관리 격자 생성, 자원 매장·대기 채집 데이터 확장점은 유지하되 고체 표면 도시를 자동 생성하지 않는다.
- 달은 `moon` 타입에서 정상적으로 편집·JSON export/import 가능해야 한다.
- 향후 랜덤 항성계/행성이 생겨도 생성기가 `systemId`, `bodyId`, `bodyKind`, 지질/환경 특성을 제공하면 같은 UI로 편집 가능해야 함.

## 6. JSON 내보내기/가져오기 계약

### 6.1 기본 원칙

- **현재 편집한 행성 하나**를 독립 JSON으로 내보내고 동일 시스템·대상의 파일을 가져올 수 있다.
- 추후 행성 묶음/항성계 일괄 export는 쉽게 확장 가능해야 하지만 이번 기본 동작을 불필요하게 크게 만들지 않는다.
- `schemaVersion`, `generatorVersion`, `grid` 매핑, 대상 ID를 검증하여 잘못된 데이터를 적용하기 전에 오류 제공.
- 사용자 내보내기 파일은 프로젝트 안의 **정적 초기 행성 프리셋/시나리오 데이터**로 가져가 사용할 수 있어야 한다. 브라우저 로컬 저장에만 의존하지 말 것.
- 모바일에서도 표준 `<input type="file" accept=".json,application/json">`을 통해 가져오고, `Blob` + 다운로드 링크로 내보내기. File System Access API 전용 구현 금지.
- JSON 가져오기 전에 **검증 → 변경 미리보기/대상·섹터 수 확인 → 명시적 적용**. 잘못된 파일을 가져오면 현재 작업 상태는 변경되지 않아야 한다.
- 기존 편집이 있는 경우 덮어쓰기 확인과, 이전 작업 내보내기/백업 경로 제공.
- 손상 파일/버전 불일치/자원 ID 오류/섹터 중복/없는 ID/잘못된 양의 값은 전체 원자적으로 거부하고 구체적인 오류 메시지 출력.
- 파일명 예시: `SPACE_surface_sol_earth_schema1.json`.

### 6.2 권장 JSON 개념 예시 (스키마는 구현 시 문서화)

```json
{
  "schemaVersion": 1,
  "kind": "planet-surface-template",
  "systemId": "sol",
  "bodyId": "earth",
  "bodyKind": "planet",
  "grid": {
    "type": "icosahedral-dual",
    "generatorVersion": 1,
    "frequency": 3,
    "orientationId": "body-local-v1",
    "cellCount": 92,
    "gridFingerprint": "computed-stable-checksum"
  },
  "geology": {
    "cells": {
      "sol:earth:surface:00024": {
        "terrain": {
          "terrainType": "mixed",
          "landFraction": 0.65,
          "waterFraction": 0.35
        },
        "deposits": [
          {
            "depositId": "ore-24-01",
            "resourceId": "ore",
            "initialReserveU": 120000,
            "discoveryTier": 1,
            "extractionDifficulty": 1
          }
        ]
      }
    }
  },
  "startingScenario": {
    "year": 2100,
    "civilizationId": "human",
    "cells": {
      "sol:earth:surface:00024": {
        "populationPersons": 42000000,
        "urbanizationRate": 0.78,
        "infrastructureLevel": 4
      }
    }
  }
}
```

**위의 수치는 모두 예시이며 2100년 지구에 대한 확정 데이터가 아니다.** 지질·인구·도시화는 편집기로 사용자가 직접 채우게 한다. `geology.cells`와 `startingScenario.cells`는 변경/설정된 셀만 저장하는 sparse override를 허용하되, 가져오기 후 **모든 타일에 대한 최종 데이터 조회가 가능**해야 한다. `grid`는 생성 파라미터로 재현하거나 전체 타일 정의를 버전 있게 내보내되 ID 안정성과 다른 브라우저 복원을 검증한다.

런타임 진행 저장은 별도 스키마(미구현). `initialReserveU`를 나중에 채굴로 덮어쓰거나, 플레이어에게 아직 발견되지 않은 지질정보와 인지 상태를 섞지 않는다.

### 6.3 편집 초안 저장

- `localStorage` 등 사용 가능한 브라우저 저장을 **시스템+행성별, 스키마 버전별**로 사용해 편집 초안 유지.
- v0.5A `space-project:administration:v1` 키·포맷과 충돌 금지.
- 저장이 실패하면 실제로 저장됐다고 알리지 말 것. 백업/내보내기를 권장하는 UI.
- 버전 불일치 시 원본 보존, 파괴적 자동 복구 금지.
- 최종 편집 결과가 실제 게임 시작 데이터로 적용되는 경로(예: `dist/data/planet-surfaces/`의 정적 파일)가 별도로 문서화되어야 한다. **개발자가 내보낸 JSON을 레포에 추가하고 로더가 읽으면 동일한 표면 상태가 재현**되어야 함.

## 7. 주소창 없는 숨겨진 개발자 진입 (모바일 필수)

현재 `main.js`의 개발 시험 항성계 컨트롤은 `?dev=1`일 때만 보인다. 모바일에 주소창이 보이지 않거나 주소 수정이 어려운 경우가 있으므로, **주소를 수정하지 않아도 개발자 모드에 진입할 수 있어야 한다.**

구현 요구:

1. 기본 HUD에서 자연스럽게 보이는 기존 `SPACE` 워드마크/로고를 **5초 이내 7회 탭/클릭**하면 개발자 모드 열기(권장 진입 동작). 또는 로고 **1.5~2초 길게 누르기**를 보조 진입으로 제공. 제스처 임계치는 하나의 상수로 관리하고 장치에서 테스트한다.
2. 일반 버튼·지도 드래그·로고의 평범한 한 번 클릭에는 반응하지 않음. 의도치 않은 진입 방지.
3. 개발자 모드가 켜지면 `개발자 도구` 드로어 및 명시적인 **`개발자 모드 종료`** 버튼 표시. 기존 `#developer-controls`/시험 항성계 선택도 이 공용 `devEnabled` 상태를 따름.
4. 기존 `?dev=1` 진입은 그대로 유지. URL 변경/새로고침/주소창 사용 없이 진입·종료 가능. 필요하다면 `sessionStorage`에 현재 탭 상태를 저장할 수 있지만 **일반 기본값은 비활성화**.
5. 개발자 도구가 활성일 때에만 표면 데이터 편집·실제 미발견 자원 조회·JSON import/export가 가능. 배속, 일반 지도, 행정구역 등의 일반 사용 기능은 영향 없음.
6. 숨겨진 동작은 인증/보안 경계가 아니므로 사용자 서버 또는 관리자 API가 없는데도 권한이 확보된 것처럼 표현하지 않는다. 파일 쓰기는 브라우저 로컬에 한정.
7. 키보드 접근, 포커스 표시, 터치 제스처 취소, 우발적 문맥 메뉴, 화면 회전, 드로어 열기/닫기 후 이벤트 리스너 누적 문제 검증.
8. PC/모바일에서 **7회 탭 진입, 종료, 재진입, `?dev=1` 호환**을 자동 브라우저 테스트.

## 8. 전체화면 진입/해제 버튼 (일반 HUD에 항상 표시)

**사용자가 직접 누를 수 있는 전체화면 버튼을 HUD에 추가한다.** 개발자 모드 전용이 아니다.

1. PC/모바일 가로 지도에서 눈에 띄되 다른 지도 버튼과 간섭하지 않는 작은 `전체화면` 아이콘 버튼을 상단 HUD 또는 지도 설정에 **항상 접근 가능**하게 배치. 작은 화면에서는 아이콘만 남겨도 된다. `aria-label`, `title`, 포커스 표시 제공.
2. 사용자 클릭/터치 이벤트에서 직접 `#map.requestFullscreen()` 등 표준 Fullscreen API 호출. **사용자 제스처 없이 시작 시 자동 전체화면 요청 금지.**
3. 현재 `document.fullscreenElement`를 기준으로 들어가기/나오기(`document.exitFullscreen()`)를 토글하고, `fullscreenchange`, `fullscreenerror`, Promise 거부를 처리. 성공 전 버튼 상태를 미리 바꾸지 않는다.
4. 미지원·권한 거부·임베디드 페이지 권한 제한에 대해 예외 없이 안내(예: `현재 브라우저에서는 전체화면을 지원하지 않습니다. 브라우저 메뉴 또는 홈 화면에 추가를 이용해 주세요.`). 사용자에게 작동한다고 거짓 안내 금지.
5. 일부 모바일 브라우저, 특히 iPhone 브라우저에서는 일반 요소의 전체화면 API 지원이 제한될 수 있다. **불가능한 브라우저 주소창 제거를 강제로 구현하거나 자동 스크롤로 흉내 내지 말 것.** 지원되는 경우만 진입하고, 대안은 텍스트로 안내.
6. 가능하면 landscape 방향 고정은 별도 선택적 향상사항이며 실패해도 전체화면 기능이 정상적이어야 함. 사용자의 기기 회전 설정을 강제로 우회하지 말 것.
7. 전체화면 전후 `ResizeObserver`, 카메라 aspect, WebGL canvas, HUD, 편집 드로어/파일 버튼의 크기·터치 영역, safe-area를 다시 검증. `100dvh`, CSS `:fullscreen`, 노치/홈 인디케이터 영역 대응.
8. 키보드 Esc/시스템 제스처로 종료했을 때 버튼 표시가 즉시 원상복구되고 행성 편집 데이터/카메라/선택이 보존되어야 함.
9. Chrome/Chromium에서 실제 전체화면 왕복 검증, 미지원 Mock/거부 Promise/iframe 권한 제한에서 실패 상태 검증, 모바일 가능한 환경에선 실제 버튼 테스트. 플랫폼이 미지원이면 그 결과를 '미지원 정상 처리'로 보고. 모든 기종 지원을 주장하지 않는다.

참고: https://developer.mozilla.org/en-US/docs/Web/API/Fullscreen_API/Guide , https://developer.mozilla.org/en-US/docs/Web/API/Element/requestFullscreen

## 9. 렌더/선택 모드 및 기존 시스템과의 통합 계약

모드의 개념을 충돌 없이 정리한다.

- **항성계 탐사 지도**: 기존 v0.5A 기초 공간 210 AU 육각 섹터.
- **항성계 행정 지도**: 기존 행정 통합·편집.
- **행성/위성 표면 지도**: 선택 천체의 구면 타일을 탐색/선택.
- **행성/위성 표면 개발자 편집**: 앞 표면 지도에서만 타일의 데이터 값을 수정.

표면 모드는 항성계 행정구역 데이터/시각화와 독립적이다. 원래 210 AU 셀은 항성계 평면에 남아 있으며 행성 자전과 같이 회전하지 않는다. 반대로 표면 타일은 선택 행성 로컬 구체에 고정되며 태양계 기초 섹터의 `(q,r)`를 사용하지 않는다.

`SystemViewer`/`ContextPanel`은 공용 천체 데이터를 주입받아 처리한다. `body.id==='earth'` 식의 하드코딩은 **기본 시나리오를 고르는 어댑터/seed 파일 외에는 금지**. `system-context`의 `bodyById`, `kind`로 지원 대상을 결정한다.

콘솔 입력/개발자 상태 전환과 UI 상태를 단일 주체에서 관리한다. `scene.js`에서 선택 판정을 따로 여러 군데 중복 구현하지 않는다. 자원 정보 패널에서 HTML injection 발생하지 않도록 사용자 정의 문자열 escape/`textContent` 사용.

## 10. 속도·성능·디바이스

- Earth f=3/92셀은 PC에서 회전·줌·선택 시 자연스럽게 보이고, 모바일 844×390 / 667×375에서도 가능해야 함.
- **모든 태양계 행성 8개와 위성**의 타일 수·이웃관계·선택·편집 데이터를 개별 검증한다. 특히 Jupiter/Saturn 같은 많은 구역의 성능 측정.
- 모든 행성에 한번에 메시/선택 표면 수천 개를 `Mesh` 개별 생성하지 말 것. 현재 선택 천체 중심으로만 레이어 활성화, 가벼운 배치 LineSegments/삼각 버퍼, 비활성 객체 캐시/메모리 가드.
- 사용자 브라우저에서 표면 보기→항성계→행정→다른 행성→표면 보기 반복 시 WebGL memory/geometry, 이벤트 리스너, DOM overlay가 누적되지 않아야 함.
- 바디 각도·카메라 시점이 변경돼도 타일이 텍스처와 함께 돌고, 같은 로컬 지리 위치를 선택함.
- 전투·채굴·인구 시뮬레이션 없이 이번 단계에서는 **기존 시계 0.1–100×, 게임 AU 거리, 행정 편집, 천문 수치, 공전/자전이 회귀 없이 유지**되어야 한다.
- 모바일 파일 가져오기/내보내기는 외부 앱/공유 메뉴에서 가능한 표준 동작 사용. 지원 미확인 API에 의존하지 않는다.

## 11. 테스트 및 완료 조건 (반드시 실제 실행)

### 11.1 순수 모델 자동 검사

- 격자 f=2/3/4/5의 타일 수 정확히 42/92/162/252, 오각형 정확히 12개, 나머지 육각형.

- 같은 천체/생성기/주파수/방향 → 모든 타일 ID·이웃·중심·면적 checksum 동일, 다른 천체는 ID 충돌 없음.
- 지구 `Planet Size 15` → 92 타일, 다른 모든 태양계 행성 → 각자 유효한 수/예상 밀도, 동일 92개를 일괄 반환하지 않음.
- 위성 `planetSize` 없음에도 표면 격자 생성, 지구·달·화성·목성·시험계 임의 행성의 구면 좌표/선택 조회.
- 반대편 또는 동일 꼭짓점 경계의 단일·결정적 선택 및 idempotent 조회.

### 11.2 데이터/JSON 검사

- 자원 `U` 단위, `ore` 유한 매장량, `alloy` 매장 금지, 크레딧과 단위 분리.
- 1 POP = 1,000,000명 정확; 1,000명→0.001 POP; 정수 인구 저장; 미설정 vs 0 구분.
- 도시화 비율 0–1, 합계 비율 검증, 가스 행성의 비육상 상태 검증.
- 지구·금성·목성·달·임의 시험계 각자 편집 → 내보내기 → 새 인스턴스 불러오기 → 완전 동일 데이터.
- 다른 행성 파일, 다른 generatorVersion/frequency/fingerprint, malformed JSON, unknown tile/ID, 잘못된 자원·수치 거부 **현재 편집 데이터 불변**.
- 천체 변경, 탭 새로고침 후 로컬 초안 복원; 저장 실패·손상 시 원본 보존·경고.
- 원본 geology 와 startingScenario 구분 유지; 미래 runtime 필드로 덮어쓰지 않음.

### 11.3 브라우저 실동작 검사

- PC 1440×1000: 현재 항성계 UI/행정/시간 제어 회귀.
- 모바일 844×390 / 667×375: 지구, 화성, 목성, 달의 표면 지도·터치 타일 선택·패널 스크롤·파일 선택·다운로드.

## 12. 코드 조직 권장안

기존 모듈을 존중하며 다음과 같은 분리를 권장한다(최종 파일명은 조정 가능).

```text
dist/src/
  planetary-surface-grid.js       # 순수 구면 dual 격자, ID, 인접, 선택 좌표
  planetary-surface-model.js      # 천체별 원본/시나리오 데이터, U/POP 검증, 스키마
  planetary-surface-io.js         # JSON 검증·가져오기/내보내기·초안 저장
  planetary-surface-view.js       # Three.js 타일 렌더·선택·하이라이트·dispose
  planetary-surface-ui.js         # 표면 모드/정보/개발자 편집 UI
  developer-mode.js               # 로고 숨김 제스처, 기존 ?dev=1와 연동
  fullscreen-control.js           # Fullscreen API 버튼·상태·지원 실패 처리
  resource-definitions.js         # ore 및 향후 전략자원 등록 계약

dist/data/planet-surfaces/         # 개발자 export를 복사해 적용하는 정적 초기 프리셋

tests/
  planetary-surface-grid.test.js
  planetary-surface-io.test.js
  browser-planet-surface.mjs
```

`planetary-surface-grid.js`는 Three.js·DOM 없이 순수 로직으로, JSON 입출력/검증도 가능한 한 순수 함수로 유지. `scene.js`에서는 기존 `createBody()`가 `spin` 노드를 보유하고 있으므로 표면 지도 레이어와 사용자 선택의 연결 지점만 추가한다. `main.js`에 모든 UI·스키마·구면 기하를 몰아 넣지 말 것.

**파일 수 늘리기 자체가 목표가 아니다.** 책임/테스트 범위를 명확히 유지하되 기존 공용 기능을 중복 재구현하지 않는다.
